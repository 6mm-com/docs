El trading embebido usualmente se introduce en un producto existente, no se lanza como un destino independiente. La mejor ruta de integración depende de dónde los usuarios ya inviertan su tiempo y qué sistema posee la identidad, los fondos y las operaciones.

<h2 id="common-scenarios">Escenarios comunes</h2>

| Escenario | Mejor punto de partida | Notas |
| --- | --- | --- |
| La app o billetera quiere una entrada de trading | Trading Widget SDK | Usa un punto de entrada nativo o H5 y abre la experiencia de trading embebida después de la autorización del usuario. |
| El corredor o plataforma de canales quiere acceso a derivados | Agent SDK + Trading Widget SDK | Mantén la relación con el cliente y la validación de backend en el sistema de socios. |
| La plataforma quiere un flujo de trading guiado | API + módulos de SDK seleccionados | Usa APIs backend para los flujos de trabajo de cuenta, transferencia y pedidos, exponiendo solo la entrada necesaria en el frontend. |
| La bolsa existente quiere mercados adicionales | Integración de liquidez + API | Combina profundidad de mercado, flujos de trabajo de cuentas y monitoreo operativo. |

<h2 id="product-decisions-before-integration">Decisiones de producto antes de la integración</h2>

- Decidir si los usuarios ingresan desde una tarjeta de página principal, página de activos, página de campaña o centro de cuentas.
- Decidir qué sistema posee el estado de inicio de sesión, la elegibilidad del usuario y la disponibilidad de país o región.
- Decidir cómo se muestran las transferencias, los registros de liquidación y los tickets de soporte al cliente a los usuarios.
- Decidir qué eventos deben ser enviados a análisis internos, CRMu operaciones de riesgo.
