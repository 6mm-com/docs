Ang mga webhook ay nagbibigay-alam sa partner backend tungkol sa mga asynchronous na pagbabago sa estado ng negosyo. Dahil maaaring subukan muli ang paghahatid, kailangang beripikahin ng bawat receiver ang signature bago i-parse ang pinagkakatiwalaang datos at dapat iproseso ang pangyayari nang pare-pareho.

<h2 id="webhook-headers">Mga header ng Webhook</h2>

| Header | Paglalarawan |
| --- | --- |
| X-Agent-Timestamp | Unix timestamp sa ilang segundo. |
| X-Agent-Nonce | Replay-protection nonce. |
| X-Agent-Signature | HMAC-SHA256 pirma. |

```text
timestamp + nonce + rawBody
```

Gamitin ang eksaktong raw request body na natanggap sa loob ng HTTP kapag nire-reconstruct ang signed value. Ang pag-parse at muling pag-serialize ng JSON muna ay maaaring baguhin ang whitespace o field order at makagawa ng ibang signature.

<h2 id="verification-flow">Daloy ng beripikasyon</h2>

1. Basahin ang timestamp, nonce, at signature headers.
2. Kunin ang hindi binagong raw request body.
3. Gumawa ng `timestamp + nonce + rawBody`.
4. Kalkulahin ang HMAC-SHA256 sa partner API lihim.
5. Ihambing ang mga nakalkula at natanggap na pirma gamit ang constant-time na paghahambing.
6. I-apply ang aprubadong timestamp-freshness at nonce-reuse checks.
7. I-parse at iproseso ang event lamang kapag nagtagumpay ang beripikasyon.

Kapag may opisyal na Agent SDK verifier, gamitin ito imbes na magpanatili ng independent signing code.

<h2 id="order-idempotency">Order idempotency</h2>

| Kaso | Paghawak |
| --- | --- |
| Paunang kahilingan sa paglilipat | Gumawa ng isang globally unique na agentOrderNo. |
| HTTP timeout | I-query ang orihinal na agentOrderNo bago gumawa ng bago. |
| PROCESSING tugon | Maghintay ng status ng webhook o query order. |
| Paulit-ulit na webhook | I-deduplicate ayon sa idempotency key at final status. |

<h2 id="recommended-idempotency-record">Inirerekomendang rekord ng idempotency</h2>

Mag-imbak ng sapat na impormasyon upang makilala ang paulit-ulit na paghahatid at ligtas na makabawi:

| Larangan | Layunin |
| --- | --- |
| Susi ng kaganapan o negosyo | Natatanging tumutukoy sa abiso o operasyon. |
| Numero ng order ng partner | Ikinokonekta ang event sa orihinal na request. |
| Payload hash | Tumutulong tukuyin ang magkasalungat na repeated payloads. |
| Kasalukuyang estado ng pagproseso | Mga natatanging natanggap, nagpoproseso, nagtagumpay, at nabigong gawain. |
| Pangwakas na kalagayan ng negosyo | Pinipigilan ang paglalapat ng terminal action nang dalawang beses. |
| Naprosesong timestamp | Sumusuporta sa mga patakaran sa imbestigasyon at pagpapanatili. |

I-commit ang business change at idempotency record sa parehong transaksyon kung maaari. Ang paulit-ulit na event ay dapat magbalik ng kilalang resulta imbes na muling ilapat ang balance, order, o user change.

<h2 id="timeout-and-retry-rule">Panuntunan ng timeout at retry</h2>

Ang HTTP timeout ay hindi nagpapatunay na nabigo ang orihinal na request. I-query ang operasyon gamit ang orihinal na `agentOrderNo`, o hintayin ang webhook nito bago magpasya kung kailangan pa ng isa pang aksyon. Ang paggawa ng bagong business order number pagkatapos ng bawat timeout ay maaaring magdulot ng dobleng paggalaw ng pondo.

<h2 id="production-checklist">Listahan ng produksyon</h2>

- Beripikahin ang pirma bago JSON parsing o pagproseso ng negosyo.
- Panatilihin ang raw body nang hiwalay mula sa na-parse na payload.
- Tanggihan ang mga luma o paulit-ulit na kahilingan ayon sa aprubadong patakaran sa integrasyon.
- Gawing ligtas ang event processing para sa paulit-ulit at out-of-order na delivery.
- I-log ang mga event ID, numero ng order ng partner, resulta ng pagproseso, at oras ng kahilingan.
- I-redact ang mga lihim at signature values mula sa mga log at support attachments.
