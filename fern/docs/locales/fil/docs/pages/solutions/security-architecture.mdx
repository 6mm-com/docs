Ang pahinang ito ay nakatuon sa kung paano dapat idisenyo ng isang partner ang isang secure 6MM integration. Para sa mas malawak na mga layer ng seguridad na ginagamit sa buong trading platform, tingnan ang [Platform Security Architecture](/fil/security-compliance/security-architecture).

Dapat pagkasunduan ang security architecture bago magsimula ang production integration. Nakakaapekto ito kung paano pinapatunayan ng partner systems ang mga user, naglalabas ng tokens, nag-iimbak ng mga sikreto, tumatanggap ng mga event, minomonitor ang operasyon, at tumutugon sa mga insidente.

<h2 id="recommended-trust-boundary">Inirerekomendang hangganan ng tiwala</h2>

| Komponent | Maaaring maglaman | Hindi dapat maglaman |
| --- | --- | --- |
| Frontend ng partner | Pampublikong konfigurasyon, panandaliang resulta ng entry, hindi sensitibong estado ng UI | Partner API secret, signing key, pribilehiyadong backend credentials |
| Partner backend | User mapping, protektadong kredensyal, signing logic, pagproseso ng webhook | Mga lihim na nailalantad sa pamamagitan ng mga sagot ng kliyente o pampublikong log |
| 6MM integration endpoints | Mga aprubadong signed request, token, at paghahatid ng webhook | Hindi napatunayang mga palagay ng partner side user |

Dapat tawagan ng partner frontend ang partner backend para sa privileged operations. Pinapatunayan ng backend ang partner user, tumatawag 6MM sa pamamagitan ng aprubadong API o SDK, at ibinabalik lamang ang panandaliang resulta na kailangan ng frontend.

<h2 id="security-layers">Mga layer ng seguridad</h2>

| Layer | Kinakailangang pokus |
| --- | --- |
| API kredensyal | Backend-only storage, rotation plan, at access control. |
| Pagpirma ng kahilingan | Pare-parehong timestamp, signature, at replay protection handling. |
| I-embed ang mga token | Panandaliang pag-isyu, pagsusuri ng pagiging karapat-dapat, at malinaw na pag-uugali ng pagpapawalang-bisa. |
| Webhooks | Signature verification, idempotency, retries, at event audit logs. |
| Mga Operasyon | Mga tungkulin sa pag-access, pag-escalate ng insidente, pagmamanman, at pagpapanatili ng ebidensya. |

<h2 id="production-control-plan">Plano sa kontrol ng produksyon</h2>

| Lugar ng kontrol | Minimum na ebidensya ng implementasyon |
| --- | --- |
| Imbakan ng kredensyal | Lokasyon ng secret-manager, may-ari ng access, paghihiwalay ng kapaligiran, at proseso ng rotation. |
| Entry ng user | Session validation, eligibility check, panandaliang daloy ng token, at failure handling. |
| Mga nilagdaan na kahilingan | Tamang kapaligiran, naka-synchronize na oras, pag-log ng kahilingan, at mga alerto sa error sa pirma. |
| Mga operasyon ng asset | Natatanging business IDs, timeout reconciliation, status queries, at operator review path. |
| Webhooks | Beripikasyon ng raw-body signature, replay controls, idempotency store, at retry-safe na pagproseso. |
| Pagmamanman | Mga alerto para sa mga pagkabigo sa authentication, abnormal na retries, webhook lag, at mga operational error. |
| Tugon sa insidente | Itinalagang may-ari, escalation channel, evidence retention, at proseso ng pagbawi ng credential. |

<h2 id="launch-review">Pagsusuri sa Paglulunsad</h2>

Bago ang produksyon:

1. I-draw ang user, token, request, asset, at webhook data flows.
2. Markahan kung saan nilikha, naiimbak, ginamit, na-log, na-rotate, at na-revoke ang bawat kredensyal.
3. Subukan ang mga expired na token, invalid na pirma, timeout, duplicate webhooks, at reconnect behavior.
4. Kumpirmahin na ang mga support team ay maaaring mahanap ang isang operasyon mula sa kanilang request o business identifier.
5. Kumpletuhin ang [Production Launch Checklist](/fil/solutions/production-launch-checklist).
