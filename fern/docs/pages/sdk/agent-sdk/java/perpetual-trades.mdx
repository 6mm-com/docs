## Example prerequisites

The Java snippets share these imports. Initialize `client` using Quick Start and obtain `platformUserId` from the saved binding. Example user/order IDs must be replaced with your own persisted values.

```java
import com.sixmm.agent.*;
import com.sixmm.agent.model.*;
import java.util.*;
```

## `listPerpetualTrades`

Request model: `PerpetualTradesRequest`.

```java
import com.sixmm.agent.model.PerpetualTradesRequest;
import com.sixmm.agent.model.PerpetualResponse;
import java.util.Collections;

PerpetualTradesRequest request = new PerpetualTradesRequest();
request.platformUserIds = Collections.singletonList("1188041528");
request.limit = 100;
request.symbol = "BTCUSDT";
request.endTime = System.currentTimeMillis();
request.startTime = request.endTime - 3_600_000L;
PerpetualResponse response = client.listPerpetualTrades(request);
System.out.println(response.data.items.size());
System.out.println(response.data.hasMore);
System.out.println(response.data.nextCursor);
```

<span data-sixmm-canonical-anchor="request-fields" aria-hidden="true"></span>

### Request fields

| Field | Java type | Required | Meaning |
| --- | --- | --- | --- |
| `platformUserIds` | `java.util.List<String>` | Conditional | 1–100 unique public IDs; required for fills and conditional orders. Omit on supported queries for direct-player scope; [] is invalid. |
| `symbol` | `String` | No | Optional trading-pair filter. |
| `orderId` | `String` | No | Ordinary order ID; not a partner transfer order number. |
| `startTime` | `Long` | No | Inclusive Unix milliseconds; use a fixed UTC history window. |
| `endTime` | `Long` | No | Exclusive Unix milliseconds. |
| `limit` | `Integer` | No | Default 500; 1–1000. |
| `cursor` | `String` | No | Use the returned nextCursor with unchanged filters; stop when hasMore is false. |

The example reads one page. For required fields, player scope, filter semantics, limit, cursor and bounded retries, follow [Query overview](/sdk/agent-sdk/java/perpetual-queries). Keep all filters unchanged while paging; do not interpret an error as an empty result.

## Trade fill details

Interface: `trades`. Requires explicit platformUserIds.

| `data` field | type | meaning |
| --- | --- | --- |
| `fillId` | string | Trade fill details ID, corresponding to this record entityId |
| `tradeId` | string | The matching transaction ID associated with the transaction; does not replace the detailed ID |
| `orderId` | string | The general order ID to which this detail belongs |
| `positionId` | string | Associated position ID |
| `symbol` | string | trading pair |
| `side` | string | This player’s buying and selling direction BUY / SELL |
| `roleType` | string | This player’s transaction character MAKER / TAKER |
| `positionSide` | string | Position direction, explained according to actual value LONG / SHORT / BOTH etc. |
| `price` | string | This transaction price |
| `quantity` | string | The quantity of this transaction is not the total quantity of the original order. |
| `tradeValue` | string | The nominal value of this transaction comes from the transaction notional |
| `handlingFee` | string | The transaction fee for this transaction retains the source symbol and accuracy, and does not take the absolute value by itself. |
| `realizedPnl` | string | The realized profit and loss corresponding to this transaction; not the real-time floating profit and loss of the current position |
| `tradedAt` | integer | Transaction time, milliseconds; use this field for time filtering |

An order may have multiple fills, which should be saved in detail. Do not merge records of different players/fill roles by tradeId and then discard their record identities.
