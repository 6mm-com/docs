Set up how visitors enter support, what they see and which intelligent services are available. Treat a setting change as a small release: save it, test the real entry and check the result.

<div className="sixmm-support-flow">

1. **Choose the setting** — Locate the tab for the behavior you want to change.
2. **Save the change** — Review the affected entry or service.
3. **Test as a visitor** — Open the real website and verify the result.

</div>


<span data-sixmm-canonical-anchor="configure-the-visitor-experience" aria-hidden="true"></span>

## Configure the visitor experience

Open **System Settings**. Available controls depend on your role and enabled tenant services.

| Tab | What to configure |
| --- | --- |
| Appearance and integration | The available visual and entry settings |
| Homepage and copy | Customer-facing homepage text and guidance |
| Conversation and timeout | Conversation behavior and timeout controls |
| Visitor dialogs | The information and prompts collected at visitor entry |
| Intelligent services | AI, retrieval and translation capabilities exposed for the tenant |
| Website integration | Domain allowlist, embed code, signed identity and language/theme integration |
| MCP connection | Service address, authorized applications and revocation |

Save settings, then verify them from the visitor entry. A preview or a successful save does not establish that a separately embedded website is already using the latest settings.

<span data-sixmm-canonical-anchor="keep-boundaries-clear" aria-hidden="true"></span>

## Keep boundaries clear

Tenant settings configure the tenant's customer support. They do not grant access to platform-wide provider keys, other tenants, recharge operations or exchange trading accounts. MCP exposes only the supported configuration fields allowed by the current role. Domain allowlist changes through MCP require confirmation.


<span data-sixmm-canonical-anchor="plan-the-initial-setup" aria-hidden="true"></span>

## Plan the initial setup

1. **Appearance and copy:** check the visible brand, homepage guidance and support wording. Keep descriptions consistent with the exchange service you actually provide.
2. **Visitor entry:** decide which information to collect and review the available prompt behavior. Test both a new visit and a returning visit where relevant.
3. **Reception behavior:** review session and timeout controls with the team that handles live conversations.
4. **Intelligent services:** verify the enabled tenant capabilities, then test a representative question or translation. A configured switch alone does not prove an upstream request succeeds.
5. **Website integration:** check the allowed website domain and use the integration guide for embed code, login identity, language and theme.
6. **MCP:** connect an external AI only after verifying the authorizing account and available permissions.

<span data-sixmm-canonical-anchor="example-a-saved-change-is-not-visible-on-your-website" aria-hidden="true"></span>

### Example: a saved change is not visible on your website

First verify the tenant and visitor entry being tested. Reload that entry, check whether the embedding website passes its own language or theme, and confirm that the intended configuration was saved. For access failures, review the allowed domain and integration configuration before repeatedly changing unrelated settings.

## Common questions

<AccordionGroup>

<Accordion title="Why can I not see a settings tab?">
Account permissions and enabled tenant services determine what is available. Ask the tenant administrator to check the relevant access rather than changing another tenant or account.
</Accordion>

<Accordion title="Where are model credentials and top-ups managed?">
Provider credentials and platform balance adjustments are outside tenant settings. Use the service arrangements agreed with the platform operator.
</Accordion>

</AccordionGroup>
