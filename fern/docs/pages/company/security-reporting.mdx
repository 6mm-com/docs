Security reports should include enough technical context for the 6MM team to assess impact and reproduce the issue safely.

<span data-sixmm-canonical-anchor="reportable-issues" aria-hidden="true"></span>

## Reportable issues

- Vulnerabilities in API, SDK, webhook, authentication, or trading entry flows.
- Suspicious production behavior that may affect trading integrity or user safety.
- Credential leakage or suspected unauthorized access.
- Abuse patterns that may affect system stability.

<span data-sixmm-canonical-anchor="include-in-the-report" aria-hidden="true"></span>

## Include in the report

- Affected environment and endpoint.
- Time range and reproduction steps.
- Logs, request IDs, webhook event IDs, or screenshots.
- Whether the issue is currently active.

<span data-sixmm-canonical-anchor="safe-reporting-guidelines" aria-hidden="true"></span>

## Safe reporting guidelines

- Do not publicly disclose an unremediated vulnerability.
- Do not access, download, change, or retain data beyond what is required to demonstrate the issue.
- Do not perform denial-of-service, destructive, social-engineering, or fund-movement testing.
- Use test accounts and the smallest safe proof of concept.
- Remove passwords, API secrets, access tokens, private keys, and unrelated personal data from attachments.

<span data-sixmm-canonical-anchor="suggested-report-format" aria-hidden="true"></span>

## Suggested report format

```text
Title:
Affected component and environment:
First observed time (UTC):
Issue status:
Technical description:
Reproduction steps:
Expected security behavior:
Observed behavior:
Potential impact:
Sanitized evidence:
Researcher or partner contact:
```

Send vulnerability and urgent security reports privately to:

[security@6mm.com](mailto:security@6mm.com)
