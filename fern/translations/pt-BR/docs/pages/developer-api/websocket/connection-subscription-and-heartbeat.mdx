Use WebSocket streams para dados de mercado e atualizações privadas do estado dos usuários que devem se manter atualizadas sem necessidade de pesquisas.

<span id="connection-url" data-sixmm-canonical-anchor="connection-url" aria-hidden="true"></span>

## Conexão URL

```text
wss://ws.6mm.com/ws
```

Fluxos privados requerem contexto de autenticação, como um token de listenKey ou acesso, conforme descrito na documentação do canal privado.

<span id="subscribe" data-sixmm-canonical-anchor="subscribe" aria-hidden="true"></span>

## Assine

```json
{ "id": "1772007814666", "op": "subscribe", "args": ["market.depth.BTCUSDT"] }
```

Reconhecimento de assinatura bem-sucedido:

```json
{
  "id": "1772007814666",
  "event": "subscribe",
  "success": true,
  "data": ["market.depth.BTCUSDT"]
}
```

<span id="unsubscribe" data-sixmm-canonical-anchor="unsubscribe" aria-hidden="true"></span>

## Desinscrição

```json
{ "id": "1772007814667", "op": "unsubscribe", "args": ["market.depth.BTCUSDT"] }
```

## Ping da aplicativo

```json
{ "id": "1772007814668", "op": "ping", "args": [] }
```

<span id="message-envelope" data-sixmm-canonical-anchor="message-envelope" aria-hidden="true"></span>

## Envelope de mensagens

Push públicos usam um envelope consistente:

```json
{
  "topic": "market.depth.BTCUSDT",
  "event": "data",
  "ts": 1772007815000,
  "data": {}
}
```

<span id="operational-recommendations" data-sixmm-canonical-anchor="operational-recommendations" aria-hidden="true"></span>

## Recomendações operacionais

- Gerar um `id` único do lado do cliente para cada assinatura, cancelamento e solicitação de ping.
- Tratar a reconexão como uma nova sessão e se inscrever novamente nos tópicos exigidos.
- Validar que o `topic` devolvido corresponde ao canal que seu serviço espera.
- Manter o processamento de mensagens idempotente quando eventos privados de ordem ou conta estão envolvidos.
- Alterações no estado da conexão do log, confirmações de assinatura e desconexões anormais.

<span id="reconnect-workflow" data-sixmm-canonical-anchor="reconnect-workflow" aria-hidden="true"></span>

## Fluxo de trabalho de reconexão

1. Feche ou descarte o soquete anterior e crie uma nova conexão.
2. Re-autenticar fluxos privados com um listenKey ou token de acesso válido.
3. Assine novamente todos os tópicos exigidos e aguarde por confirmações bem-sucedidas.
4. Substituir o estado do livro de ordens local por um novo snapshot antes de aplicar atualizações incrementais.
5. Reconciliar ordens abertas, posições e saldos por meio de REST caso eventos privados possam ter sido perdidos.

Use backoff exponencial limitado com jitter para tentativas de reconexão. Um cliente que reconecta continuamente deve alertar os operadores em vez de tentar indefinidamente sem visibilidade.

<span id="heartbeat-and-stale-connections" data-sixmm-canonical-anchor="heartbeat-and-stale-connections" aria-hidden="true"></span>

## Batimentos cardíacos e conexões estagnadas

- Rastrear a mensagem de entrada mais recente e o reconhecimento de ping bem-sucedido.
- Utilizar o intervalo de batimentos cardíacos e o limiar de ociosidade aprovados para o ambiente de produção.
- Tratar uma conexão como obsoleta quando o limiar configurado é ultrapassado, mesmo que o soquete TCP ainda pareça aberto.
- Não reutilizar assinaturas de um socket antigo; reassinar explicitamente após cada reconexão.
