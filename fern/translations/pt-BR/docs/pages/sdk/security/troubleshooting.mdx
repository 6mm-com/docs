Comece pelo ambiente, carimbo de tempo e identificador de negócio da operação falhada. Uma verificação estruturada geralmente separa problemas de configuração de autenticação, rede e processamento assíncrono.

<span id="diagnostic-order" data-sixmm-canonical-anchor="diagnostic-order" aria-hidden="true"></span>

## Ordem diagnóstica recomendada

1. Confirme o ambiente afetado e a URL base.
2. Registre o intervalo de tempo UTC e a primeira solicitação que não tenha falhado.
3. Identifique o módulo: Trading Widget, Agent SDK, REST API, WebSocket, ou webhook.
4. Capturar o ID da solicitação, ID do usuário do parceiro, `agentOrderNo`, ID do pedido ou ID do evento do webhook.
5. Verifique códigos recentes, credenciais, listas brancas IP ou mudanças de implantação.
6. Reproduzir com o menor caso de teste seguro.

<span id="trading-widget-issues" data-sixmm-canonical-anchor="trading-widget-issues" aria-hidden="true"></span>

## Trading Widget questões

| Sintoma | Causa provável | Corrigir |
| --- | --- | --- |
| O iframe solicita o domínio local do parceiro | baseUrl está faltando | Passe baseUrl: 'https://app.6mm.com'. |
| O iframe é invisível ou muito curto | O recipiente principal não tem altura | Defina a altura do recipiente ou a altura da passagem. |
| token_provider_missing | O modo partner-token não possui provedor | Adicionar autenticaçãotokenProvider. |
| auth_exchange_failed | Token embed inválido, expirado ou incompatível | Verifique a resposta do token backend e channelId. |

<span id="agent-sdk-issues" data-sixmm-canonical-anchor="agent-sdk-issues" aria-hidden="true"></span>

## Agent SDK questões

| Sintoma | Causa provável | Corrigir |
| --- | --- | --- |
| Assinatura rejeitada | Segredo errado, desvio de clock ou campos de assinatura alterados manualmente | Deixe SDK gerar campos de assinatura e sincronizar o tempo do servidor. |
| Risco de movimento de fundos duplicados | Novo número de pedido usado após o tempo de espera | Consulte primeiro por agentOrderNo original. |
| PROCESSING tratado como fracasso | Estado pendente mal interpretado | Espere pelo webhook ou ligue para queryOrder. |
| Webhook processado várias vezes | Comportamento de retentar sem idempotência | Adicionar chaves de idempotência e verificações de estado final. |

<span id="evidence-to-capture" data-sixmm-canonical-anchor="evidence-to-capture" aria-hidden="true"></span>

## Evidências a serem capturadas

| Integração | Evidências úteis |
| --- | --- |
| Trading Widget | Página URL, caminho de SDK versão, console do navegador, requisições de rede falhadas, carga útil `onError` e dimensões do contêiner. |
| Agent SDK | SDK idioma/versão, URL base, UTC carimbo de data, ID de requisição, `agentOrderNo`, código de resposta e logs sanitizados. |
| Webhook | Tempo de entrega, chave de evento ou negócio, resultado de validação de assinatura, estado de processamento e hash do corpo bruto sanitizado. |
| REST API | Método, caminho, ambiente, ID de requisição, código de resposta e parâmetros sanitizados. |

Nunca inclua senhas, tokens de acesso, API segredos, assinaturas completas, chaves privadas ou dados pessoais não editados nos diagnósticos.

<span id="before-escalating" data-sixmm-canonical-anchor="before-escalating" aria-hidden="true"></span>

## Antes de escalar

- Retentar somente quando a operação estiver documentada como segura para tentar novamente.
- Após um timeout, consulte o identificador original do negócio em vez de criar um novo.
- Confirmar o clock do sistema e o ambiente de credenciais para erros de assinatura.
- Preservar a primeira falha e quaisquer resultados de tentativas posteriores.
- Use o [Modelo de Solicitação de Suporte](/pt-BR/resources/support-request-template) para enviar um relatório completo e redigido.
