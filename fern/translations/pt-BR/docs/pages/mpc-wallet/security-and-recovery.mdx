A preparação da segurança começa com o acordo de custódia selecionado. Proteção de conta, aprovação de transações, participação de MPC e material de recuperação têm finalidades diferentes.

<span id="assign-responsibilities" data-sixmm-canonical-anchor="assign-responsibilities" aria-hidden="true"></span>

## Atribuir responsabilidades

Visualização de rotina separada, início de transferência, aprovação, administração de membros e gerenciamento de credenciais de desenvolvedor onde o produto permitir. Verifique as permissões no espaço de trabalho pretendido; o acesso a um espaço de trabalho não estabelece autoridade sobre outro.

Para fluxos de trabalho empresariais, defina quem analisa as alterações de destino e as solicitações de saída. Para assinatura do dispositivo, o participante deve inspecionar a rede exibida, ativo, quantidade, destino e contexto antes de aceitar. A confirmação de um dispositivo não deve ser tratada como um pedido de aprovação cega.

<span id="keep-credentials-distinct" data-sixmm-canonical-anchor="keep-credentials-distinct" aria-hidden="true"></span>

## Mantenha as credenciais distintas

| Material | Propósito |
| --- | --- |
| Autenticação de conta | Acesse o aplicativo do usuário |
| API chave e segredo | Autenticar solicitações de back-end API |
| Chave de autorização do cliente | Autorizar o conteúdo de uma retirada API quando necessário |
| MPC compartilhamento de chave | Participe do processo de assinatura distribuída da carteira |
| Material de backup e recuperação | Restaure a participação ou execute o procedimento de recuperação suportado |

Armazene-os de acordo com suas próprias responsabilidades. Uma chave API não é um compartilhamento MPC; redefinir a senha de uma conta não é uma operação de recuperação de carteira. Faça upload das chaves públicas somente por meio do fluxo de registro relevante, nunca das chaves privadas correspondentes.

<span id="prepare-recovery-before-use" data-sixmm-canonical-anchor="prepare-recovery-before-use" aria-hidden="true"></span>

## Prepare a recuperação antes de usar

Registre os participantes necessários, proprietários de backup e etapas de recuperação durante a integração. Mantenha os backups em locais apropriados separados e teste o procedimento de recuperação compatível em um ambiente controlado. Considere um dispositivo perdido e uma interrupção no serviço da plataforma.

A autocustódia não permite que a plataforma recrie ações de clientes ausentes. Se restarem poucos participantes utilizáveis ​​e backups para satisfazer os requisitos da carteira, o acesso aos ativos poderá ser perdido. A custódia conjunta de chaves também necessita de um acordo de recuperação documentado; não presuma que a participação na plataforma garante a recuperação.

<span id="handle-an-unavailable-participant" data-sixmm-canonical-anchor="handle-an-unavailable-participant" aria-hidden="true"></span>

## Lidar com um participante indisponível

Primeiro, distinga um problema de conexão temporário, um dispositivo indisponível e perda de material de assinatura. Revise o status da sessão e do dispositivo e use o processo de recuperação ou substituição compatível. Não apague um dispositivo, altere a identidade de assinatura do aplicativo ou presuma que os compartilhamentos podem ser movidos antes de verificar os requisitos de recuperação.

A disponibilidade do backup não é prova de um teste de recuperação concluído. Confirme quais procedimentos e ferramentas estão incluídos na sua versão antes de confiar neles.
