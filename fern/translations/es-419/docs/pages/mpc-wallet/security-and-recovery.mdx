La preparación de seguridad comienza con el acuerdo de custodia seleccionado. La protección de cuenta, la aprobación de transacciones, la MPC participación y el material de recuperación tienen diferentes propósitos.

<span id="assign-responsibilities" data-sixmm-canonical-anchor="assign-responsibilities" aria-hidden="true"></span>

## Asignar responsabilidades

Separe la visualización de rutinas, el inicio de transferencias, la aprobación, la administración de miembros y la gestión de credenciales de desarrollador cuando el producto lo permita. Verifique los permisos en el espacio de trabajo previsto; El acceso a un espacio de trabajo no establece autoridad sobre otro.

Para flujos de trabajo empresariales, acuerde quién revisa los cambios de destino y las solicitudes salientes. Para la firma del dispositivo, el participante debe inspeccionar la red, el activo, la cantidad, el destino y el contexto mostrados antes de aceptar. La confirmación de un dispositivo no debe tratarse como una solicitud de aprobación ciega.

<span id="keep-credentials-distinct" data-sixmm-canonical-anchor="keep-credentials-distinct" aria-hidden="true"></span>

## Mantenga las credenciales distintas

| Material | Objetivo |
| --- | --- |
| Autenticación de cuenta | Acceder a la aplicación de usuario |
| API clave y secreto | Autenticar solicitudes de backend API |
| Clave de autorización del cliente | Autorizar el contenido de un API retiro cuando sea necesario |
| MPC clave compartida | Participe en el proceso de firma distribuida de la billetera. |
| Material de respaldo y recuperación. | Restaurar la participación o realizar el procedimiento de recuperación admitido. |

Guárdelos según sus propias responsabilidades. Una clave API no es un recurso compartido MPC; restablecer la contraseña de una cuenta no es una operación de recuperación de billetera. Cargue claves públicas únicamente a través del flujo de registro correspondiente, nunca sus correspondientes claves privadas.

<span id="prepare-recovery-before-use" data-sixmm-canonical-anchor="prepare-recovery-before-use" aria-hidden="true"></span>

## Prepare la recuperación antes de su uso.

Registre los participantes requeridos, los propietarios de las copias de seguridad y los pasos de recuperación durante la incorporación. Mantenga las copias de seguridad en ubicaciones apropiadas separadas y pruebe el procedimiento de recuperación admitido en un entorno controlado. Considere tanto la pérdida de un dispositivo como una interrupción del servicio de la plataforma.

La autocustodia no permite que la plataforma recree los fragmentos de clave de clientes faltantes. Si quedan muy pocos participantes utilizables y copias de seguridad para satisfacer los requisitos de la billetera, se puede perder el acceso a los activos. La custodia conjunta de claves también necesita un acuerdo de recuperación documentado; No asuma que la participación en la plataforma garantiza la recuperación.

<span id="handle-an-unavailable-participant" data-sixmm-canonical-anchor="handle-an-unavailable-participant" aria-hidden="true"></span>

## Manejar un participante no disponible

Primero distinga un problema de conexión temporal, un dispositivo no disponible y material de firma perdido. Revise la sesión y el estado del dispositivo, luego utilice el proceso de recuperación o reemplazo admitido. No borre un dispositivo, no cambie la identidad de firma de su aplicación ni asuma que los recursos compartidos se pueden mover antes de verificar los requisitos de recuperación.

La disponibilidad de la copia de seguridad no es prueba de una prueba de recuperación completa. Confirme qué procedimientos y herramientas están incluidos en su autorización antes de confiar en ellos.
