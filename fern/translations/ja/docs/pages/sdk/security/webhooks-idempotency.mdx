Webhooks 非同期のビジネス状態の変更についてパートナー バックエンドに通知します。配信は再試行される可能性があるため、すべての受信者は信頼できるデータを解析する前に署名を検証し、イベントをべき等に処理する必要があります。

<span id="webhook-headers" data-sixmm-canonical-anchor="webhook-headers" aria-hidden="true"></span>

## Webhook ヘッダー

| ヘッダ | 説明 |
| --- | --- |
| X-エージェント-タイムスタンプ | 秒単位の Unix タイムスタンプ。 |
| X-エージェント-ノンス | リプレイ保護ノンス。 |
| X エージェントの署名 | HMAC-SHA256 の署名。 |

```text
timestamp + nonce + rawBody
```

署名された値を再構築するときは、HTTP で受信した正確な生のリクエスト本文を使用します。最初に JSON を解析して再シリアル化すると、空白やフィールドの順序が変更され、別の署名が生成される可能性があります。

<span id="verification-flow" data-sixmm-canonical-anchor="verification-flow" aria-hidden="true"></span>

## 検証の流れ

1. タイムスタンプ、ノンス、署名ヘッダーを読み取ります。
2. 変更されていない生のリクエスト本文をキャプチャします。
3. `timestamp + nonce + rawBody` をビルドします。
4. パートナー API のシークレットを使用して HMAC-SHA256 を計算します。
5. 定数時間比較を使用して、計算された署名と受信された署名を比較します。
6. 承認されたタイムスタンプの鮮度チェックと非再利用チェックを適用します。
7. 検証が成功した場合にのみ、イベントを解析して処理します。

公式の Agent SDK 検証ツールが利用可能な場合は、独立した署名コードを維持する代わりにそれを使用します。

<span id="order-idempotency" data-sixmm-canonical-anchor="order-idempotency" aria-hidden="true"></span>

## 順序冪等性

| 場合 | 取り扱い |
| --- | --- |
| 最初の転送リクエスト | グローバルに一意の agentOrderNo を 1 つ作成します。 |
| HTTP タイムアウト | 新しいものを作成する前に、元の agentOrderNo をクエリします。 |
| PROCESSING 応答 | webhook を待つか、注文ステータスを問い合わせてください。 |
| 繰り返しwebhook | 冪等性キーと最終ステータスによって重複を排除します。 |

<span id="recommended-idempotency-record" data-sixmm-canonical-anchor="recommended-idempotency-record" aria-hidden="true"></span>

## 推奨されるべき等性レコード

繰り返しの配信を認識し、安全に回復するために十分な情報を保存します。

| 分野 | 目的 |
| --- | --- |
| イベントまたはビジネスキー | 通知または操作を一意に識別します。 |
| パートナー注文番号 | イベントを元のリクエストに接続します。 |
| ペイロードハッシュ | 競合する反復ペイロードを特定するのに役立ちます。 |
| 現在の処理状態 | 受信した作業、処理中の作業、成功した作業、失敗した作業を区別します。 |
| 最終的な営業状況 | 終了アクションが 2 回適用されるのを防ぎます。 |
| 処理されたタイムスタンプ | 調査と保持ポリシーをサポートします。 |

可能な場合は、ビジネス変更と冪等性レコードを同じトランザクションでコミットします。繰り返されるイベントでは、残高、順序、またはユーザーの変更を再度適用するのではなく、既知の結果を返す必要があります。

<span id="timeout-and-retry-rule" data-sixmm-canonical-anchor="timeout-and-retry-rule" aria-hidden="true"></span>

## タイムアウトと再試行のルール

HTTP タイムアウトは、元のリクエストが失敗したことを証明するものではありません。元の `agentOrderNo` を使用して操作をクエリするか、その webhook を待ってから、別のアクションが必要かどうかを判断します。タイムアウトが発生するたびに新しい業務注文番号を作成すると、重複した資金移動が発生する可能性があります。

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## 製作チェックリスト

- JSON の解析またはビジネス処理の前に署名を検証してください。
- 解析されたペイロードから独立して生の本体を保存します。
- 承認された統合ポリシーに従って、古いリクエストまたは再実行されたリクエストを拒否します。
- 繰り返しの配信や順序どおりでない配信に対してイベント処理を安全にします。
- イベント ID、パートナー注文番号、処理結果、リクエスト時刻を記録します。
- ログからのシークレットと署名値を編集し、添付ファイルをサポートします。

## 資金と環境の境界線

元の契約転送 webhook および `queryOrder` フローは、資金調達に自動的には適用されません。 `queryWalletTransfer` と元の注文環境を使用して資金調達操作を確認します。資金には `status` が使用されます。元の契約転送応答では `orderStatus` を使用します。成功した HTTP 応答または `code=0` 自体は、資金が移動したことを証明するものではありません。

明示的にシミュレートされた契約転送通知には `environment=SIMULATED` が含まれます。まず生の本文を確認し、次にユーザー、金額、注文 ID、および環境を保存されたローカル ビジネス注文と比較して確認します。
