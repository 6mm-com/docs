セキュリティの準備は、選択した保管手配から始まります。アカウントの保護、トランザクションの承認、MPC への参加、および回復資料は異なる目的を果たします。

<span id="assign-responsibilities" data-sixmm-canonical-anchor="assign-responsibilities" aria-hidden="true"></span>

## 責任を割り当てる

製品で許可されている場合は、日常的な表示、転送の開始、承認、メンバー管理、および開発者の資格情報管理を個別に実行します。目的のワークスペースの権限を確認してください。あるワークスペースにアクセスしても、別のワークスペースに対する権限は確立されません。

エンタープライズ ワークフローの場合、宛先の変更と送信リクエストを誰がレビューするかについて合意します。デバイス署名の場合、参加者は受け入れる前に、表示されたネットワーク、資産、金額、宛先、およびコンテキストを検査する必要があります。デバイスの確認を、盲目的な承認プロンプトとして扱うべきではありません。

<span id="keep-credentials-distinct" data-sixmm-canonical-anchor="keep-credentials-distinct" aria-hidden="true"></span>

## 資格情報を区別しておく

| 材料 | 目的 |
| --- | --- |
| アカウント認証 | ユーザーアプリケーションにアクセスする |
| API キーとシークレット | バックエンド API リクエストを認証する |
| 顧客認証キー | 必要に応じて、API 出金の内容を承認します |
| MPC キー共有 | ウォレットの分散署名プロセスに参加する |
| バックアップおよびリカバリ資料 | 参加を復元するか、サポートされている回復手順を実行します |

各自の責任に従って保管してください。 API キーは MPC 共有ではありません。アカウントのパスワードのリセットはウォレットの回復操作ではありません。公開キーは関連する登録フローを通じてのみアップロードし、対応する秘密キーはアップロードしないでください。

<span id="prepare-recovery-before-use" data-sixmm-canonical-anchor="prepare-recovery-before-use" aria-hidden="true"></span>

## 使用前にリカバリの準備をする

オンボーディング中に必要な参加者、バックアップ所有者、およびリカバリ手順を記録します。バックアップを別の適切な場所に保管し、サポートされている回復手順を制御された環境でテストします。デバイスの紛失とプラットフォーム サービスの停止の両方を考慮してください。

自己保管では、プラットフォームが失われた顧客の共有を再作成することはできません。ウォレットの要件を満たすために使用可能な参加者とバックアップが少なすぎる場合、資産へのアクセスが失われる可能性があります。共同カストディには文書による回復取り決めも必要です。プラットフォームへの参加によって回復が保証されるとは考えないでください。

<span id="handle-an-unavailable-participant" data-sixmm-canonical-anchor="handle-an-unavailable-participant" aria-hidden="true"></span>

## 参加できない参加者を処理する

まず、一時的な接続の問題、使用できないデバイス、署名資料の紛失を区別します。セッションとデバイスのステータスを確認し、サポートされている回復または交換プロセスを使用します。回復要件を確認する前に、デバイスを消去したり、アプリケーション署名 ID を変更したり、共有を移動できると想定したりしないでください。

バックアップの可用性は、リカバリ テストが完了したことを証明するものではありません。どの手順やツールがリリースに含まれているかを信頼する前に確認してください。
