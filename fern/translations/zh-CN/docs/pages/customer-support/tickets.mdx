把无法在一次聊天中解决的问题留在可跟进的记录里。区分记录类型、明确处理人并及时更新进度，让接班客服知道下一步要做什么。

<div className="sixmm-support-flow">

1. **区分记录** — 选择客服工单、用户工单或反馈。
2. **调查与分配** — 阅读描述，确认由谁继续处理。
3. **更新结果** — 维护进度，核对保存后的状态。

</div>


<span id="choose-the-correct-record" data-sixmm-canonical-anchor="choose-the-correct-record" aria-hidden="true"></span>

## 区分三类记录

进入 **工单管理**，选择对应标签。

| 记录 | 用途 |
| --- | --- |
| 客服工单 | 由客服团队创建和维护的处理任务 |
| 用户工单 | 访客提交、需要后续跟进的问题 |
| 用户反馈 | 通过反馈入口提交的建议或问题 |

<span id="handle-a-case" data-sixmm-canonical-anchor="handle-a-case" aria-hidden="true"></span>

## 处理一个问题

查看描述、联系方式、关联会话和记录提供的附件，分配合适的处理人，并随进展更新状态。客服工单使用对应的编辑功能，用户工单和反馈有各自的可操作范围。

修改状态本身不代表用户已经收到邮件或聊天回复。需要回复时，通过实际可用的沟通渠道联系用户，并确认发送结果。个人信息应保留在已授权的租户处理流程内。

<span id="use-mcp-for-triage" data-sixmm-canonical-anchor="use-mcp-for-triage" aria-hidden="true"></span>

## 使用 MCP 辅助分流

可以让连接的 AI 查询未解决事项、按问题类型整理并起草回复。正式修改处理人或状态前核对目标记录。创建客服工单与访客提交用户工单是不同流程，不能把一种工具理解成支持另一种操作。通过 MCP 删除工单需要确认。


<span id="use-status-and-priority-deliberately" data-sixmm-canonical-anchor="use-status-and-priority-deliberately" aria-hidden="true"></span>

## 用好状态和优先级

客服工单提供待处理、处理中、已解决和已关闭等状态；用户工单与反馈使用各自页面提供的状态操作，不要把三个标签当成完全相同的流程。

| 信息 | 如何使用 |
| --- | --- |
| 工单编号 | 交接时定位同一条记录，避免只凭用户昵称查找。 |
| 问题描述与关联会话 | 了解问题背景，以及之前已经沟通过什么。 |
| 分配客服或处理人 | 明确下一步由谁负责跟进。 |
| 客服工单优先级 | 区分处理紧急程度；优先级高不代表状态已经完成。 |
| 创建与解决时间 | 按选定的时间口径查看处理过程。 |

<span id="example-an-issue-needs-technical-investigation" data-sixmm-canonical-anchor="example-an-issue-needs-technical-investigation" aria-hidden="true"></span>

### 示例：问题需要技术排查

1. 打开原始记录，整理已有信息中的发生时间、问题页面和可复现步骤。
2. 有关联会话时先查看聊天记录，避免让用户重复提供已经记录的信息。
3. 分配合适的处理人，随调查进度更新状态；内部备注保持客观、具体。
4. 问题确认解决后更新结果，通过可用渠道联系用户，并再次核对记录是否保存成功。

## 常见问题

<AccordionGroup>

<Accordion title="改成已解决会自动通知用户吗？">
状态变化本身不能证明邮件或聊天消息已经发送，需要另行确认实际沟通渠道及发送结果。
</Accordion>

<Accordion title="为什么搜不到工单？">
检查是否选对记录标签，以及日期口径、时间范围、状态和处理人筛选；先清除不必要的条件再查找。
</Accordion>
