Le richieste Agent SDK vengono autenticate con un segreto del partner API. Mantieni il segreto all'interno di un servizio backend affidabile e lascia che SDK generi campi di firma quando possibile.

> **Due protocolli di firma**
>
> La firma Agent SDK utilizza campi di richiesta ordinati, un timestamp basato sui secondi e un nonce. Le richieste dirette Developer API utilizzano il processo separato descritto in [Richiedi la firma](/it/developer-api/request-signing). Non riutilizzare un formato di payload per un altro.

<span id="signing-rule" data-sixmm-canonical-anchor="signing-rule" aria-hidden="true"></span>

## Regola di firma

Per le richieste Agent SDK:

1. Escludere il campo `sign`.
2. Omettere i campi con valori vuoti.
3. Ordina i nomi dei campi rimanenti nell'ordine ASCII.
4. Unisci i campi come `k=v&k2=v2`.
5. Calcola la firma esadecimale HMAC-SHA256 con `apiSecret`.

I valori dell'array vengono serializzati come compatti JSON prima di unirsi al payload della firma. Ad esempio, `platformUserIds` viene indicato come `["1188041528"]`, fornendo `platformUserIds=["1188041528"]` nel payload `k=v`. Conserva l'ordine degli elementi dell'array, le virgolette doppie e gli ID delle stringhe; non inserire spazi di formattazione né utilizzare Java `List.toString()` (ad esempio `[1188041528]`). Il SDK gestisce questa serializzazione automaticamente.

Il SDK dovrebbe creare questo valore dagli stessi dati che invia. La modifica di un campo firmato dopo la generazione della firma causa il fallimento della verifica.

<span id="sdk-managed-fields" data-sixmm-canonical-anchor="sdk-managed-fields" aria-hidden="true"></span>

## SDK-campi gestiti

| Campo | Fonte | Descrizione |
| --- | --- | --- |
| agentCode | SDK configurazione | Codice agente partner. |
| timestamp | Ora corrente del server | Timestamp Unix in secondi. |
| nonce | Valore casuale sicuro | Stringa casuale di protezione dalla riproduzione. |
| cartello | HMAC-SHA256 | Richiedi la firma. |
| valuta | Valuta predefinita | Utilizzato quando il trasferimento/conto APIs omette la valuta. |

<span id="secret-storage" data-sixmm-canonical-anchor="secret-storage" aria-hidden="true"></span>

## Deposito segreto

- Carica `apiSecret` da un gestore segreto backend o da una configurazione runtime protetta.
- Non inserire mai il segreto in bundle frontend, app mobili, client desktop, screenshot o ticket di supporto.
- Mantieni separate le credenziali per lo sviluppo, la gestione temporanea e la produzione.
- Limitare l'accesso ai servizi e agli operatori che lo richiedono.
- Oscura le firme delle richieste, i valori di autorizzazione e i segreti dai log.
- Revocare e sostituire le credenziali quando si sospetta un'esposizione.

<span id="clock-and-replay-protection" data-sixmm-canonical-anchor="clock-and-replay-protection" aria-hidden="true"></span>

## Protezione orologio e riproduzione

Il SDK include `timestamp` e `nonce` per ridurre il rischio di rigiocabilità. Mantieni sincronizzati gli orologi di backend e non riutilizzare un nonce costruito manualmente. Se la convalida della firma fallisce, conferma il segreto configurato, l'ora del server, i campi serializzati e l'ambiente prima di riprovare.

<span id="integration-checklist" data-sixmm-canonical-anchor="integration-checklist" aria-hidden="true"></span>

## Lista di controllo per l'integrazione

| Controllo | Risultato atteso |
| --- | --- |
| Posizione segreta | Archiviazione segreta solo backend. |
| Ambiente | La base URL e la credenziale appartengono allo stesso ambiente. |
| Movimentazione sul campo | SDK genera `timestamp`, `nonce` e `sign`. |
| Registrazione | Gli ID aziendali rimangono visibili mentre le credenziali vengono oscurate. |
| Rotazione | Il proprietario delle credenziali e il processo di sostituzione sono documentati. |
