Il trading embedded viene solitamente introdotto in un prodotto esistente, non lanciato come destinazione autonoma. Il miglior percorso di integrazione dipende da dove gli utenti già spendono il tempo e da quale sistema possiede identità, fondi e operazioni.

<h2 id="common-scenarios">Scenari comuni</h2>

| Scenario | Il miglior punto di partenza | Note |
| --- | --- | --- |
| App o wallet richiede una voce di trading | Trading Widget SDK | Usa un punto di ingresso nativo o H5 e apri l'esperienza di trading embedded dopo l'autorizzazione dell'utente. |
| Il broker o la piattaforma di canale desidera l'accesso ai derivati | Agent SDK + Trading Widget SDK | Mantieni la relazione con il cliente e la validazione backend nel sistema dei partner. |
| La piattaforma desidera un flusso di trading guidato | API + moduli SDK selezionati | Usa API backend per i flussi di lavoro di conto, trasferimento e ordine, esponendo solo l'accesso frontend necessario. |
| La borsa esistente vuole mercati aggiuntivi | Integrazione liquidità + API | Unisci profondità di mercato, flussi di lavoro degli account e monitoraggio operativo. |

<h2 id="product-decisions-before-integration">Decisioni di prodotto prima dell'integrazione</h2>

- Decidere se gli utenti entrano da una scheda homepage, una pagina di asset, una pagina campagna o un centro account.
- Decidere quale sistema possiede lo stato di accesso, l'idoneità dell'utente e la disponibilità di paese o regione.
- Decidere come i trasferimenti, i registri di saldo e i ticket di assistenza clienti vengono mostrati agli utenti.
- Decidere quali eventi devono essere inoltrati all'analisi interna, al CRMo alle operazioni di rischio.
