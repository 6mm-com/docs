Ang white-label exchange ay nangangailangan ng higit pa sa frontend shell. Ang karanasan ng user ay nakadepende sa maaasahang core modules sa likod ng trading, accounts, risk, at settlement.

<h2 id="core-modules">Core modules</h2>

| Module | Papel |
| --- | --- |
| Pagtutugma at lifecycle ng order | Humahawak ng order submission, matching state, cancellation, at execution records. |
| Sistema ng account at posisyon | Pinananatili ang balanse, kalagayan ng margin, posisyon, at availability sa trading. |
| Mga kontrol sa panganib | Kinokoordina ang leverage, margin, liquidation, at abnormal na pag-uugali sa merkado. |
| Datos ng merkado | Ipinapamahagi ang mga presyo, lalim, trades, at datos ng tsart sa mga trading interface. |
| Pamayanan at mga tala | Pinananatiling naka-align ang kasaysayan ng trading, pagbabago sa balanse, at mga operational record. |

<h2 id="documentation-path">Landas ng dokumentasyon</h2>

Magsimula sa trading rules bago API integration. Dapat pareho ang pag-unawa ng mga product, operations, at development teams sa mga uri ng order, margin behavior, fees, at liquidity logic.

<h2 id="implementation-questions">Mga tanong tungkol sa implementasyon</h2>

- Anong mga uri ng order at kondisyon ang naka-expose sa mga gumagamit?
- Aling serbisyo ang may-ari ng symbol rules, precision validation, at trading availability?
- Paano pinag-uugnay ang mga talaan ng order, trade, position, balance, at settlement?
- Aling mga identifier ang nananatiling matatag sa mga tugon ng REST , WebSocket events, at partner records?
- Anong monitoring at rollback path ang naaangkop kapag hindi na available ang matching, risk, o market data?

Sagutin ang mga tanong na ito bago mag-develop ng frontend upang ang pag-uugali ng produkto, API handling, operasyon, at suporta ay gumamit ng parehong trading model.
