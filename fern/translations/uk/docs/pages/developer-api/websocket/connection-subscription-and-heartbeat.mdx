Використовуйте WebSocket потоки для ринкових даних та приватних оновлень стану користувачів, які мають залишатися актуальними без опитувань.

<span id="connection-url" data-sixmm-canonical-anchor="connection-url" aria-hidden="true"></span>

## Зв'язок URL

```text
wss://ws.6mm.com/ws
```

Приватні потоки потребують контексту автентифікації, такого як listenKey або токен доступу, як описано в документації приватного каналу.

<span id="subscribe" data-sixmm-canonical-anchor="subscribe" aria-hidden="true"></span>

## Підписатися

```json
{ "id": "1772007814666", "op": "subscribe", "args": ["market.depth.BTCUSDT"] }
```

Успішне підтвердження підписки:

```json
{
  "id": "1772007814666",
  "event": "subscribe",
  "success": true,
  "data": ["market.depth.BTCUSDT"]
}
```

<span id="unsubscribe" data-sixmm-canonical-anchor="unsubscribe" aria-hidden="true"></span>

## Відписатися

```json
{ "id": "1772007814667", "op": "unsubscribe", "args": ["market.depth.BTCUSDT"] }
```

<span id="application-ping" data-sixmm-canonical-anchor="application-ping" aria-hidden="true"></span>

## Пінг застосування

```json
{ "id": "1772007814668", "op": "ping", "args": [] }
```

<span id="message-envelope" data-sixmm-canonical-anchor="message-envelope" aria-hidden="true"></span>

## Конверт повідомлення

Публічні просування використовують узгоджену оболонку:

```json
{
  "topic": "market.depth.BTCUSDT",
  "event": "data",
  "ts": 1772007815000,
  "data": {}
}
```

<span id="operational-recommendations" data-sixmm-canonical-anchor="operational-recommendations" aria-hidden="true"></span>

## Оперативні рекомендації

- Генерувати унікальний клієнтський `id` для кожного запиту на підписку, відписку та пінг.
- Розглядайте повторне підключення як нову сесію та повторно підписуйтеся на необхідні теми.
- Перевірити, чи повернений `topic` відповідає каналу, який очікує ваш сервіс.
- Підтримувати ідемпотентну обробку повідомлень, коли йдеться про приватні замовлення або події облікового запису.
- Зміни стану з'єднання журналу, підтвердження підписки та аномальні відключення.

<span id="reconnect-workflow" data-sixmm-canonical-anchor="reconnect-workflow" aria-hidden="true"></span>

## Робочий процес повторного підключення

1. Закрийте або відкиньте попередній роз'єм і створіть нове з'єднання.
2. Повторна автентифікація приватних потоків за допомогою дійсного listenKey або доступного токену.
3. Підпишіться на всі необхідні теми і чекайте на успішні подяки.
4. Замініть стан локальної книги замовлень на новий знімок перед поступовими оновленнями.
5. Узгодити відкриті ордери, позиції та баланси через REST , якщо приватні події могли бути пропущені.

Використовуйте обмежене експоненціальне відключення з джиттером для спроб повторного підключення. Клієнт, що постійно підключається, повинен попереджати операторів замість безкінечних повторних спроб без видимості.

<span id="heartbeat-and-stale-connections" data-sixmm-canonical-anchor="heartbeat-and-stale-connections" aria-hidden="true"></span>

## Серцебиття та застарілі зв'язки

- Відстежувати останнє вхідне повідомлення та успішне підтвердження пінгу.
- Використовуйте інтервал серцебиття та поріг очікування, дозволений для виробничого середовища.
- Вважати з'єднання застарілим при перевищенні налаштованого порогу, навіть якщо роз'єм TCP все ще виглядає відкритим.
- Не використовувати повторно підписки зі старого сокета; повторно підписуватися явно після кожного повторного підключення.
