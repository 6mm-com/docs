Відкликання — це асинхронна бізнес-операція. Успішна відповідь HTTP означає, що запит оброблено; він не встановлює, що кошти надійшли по мережі.

<span id="persist-one-business-identifier" data-sixmm-canonical-anchor="persist-one-business-identifier" aria-hidden="true"></span>

## Зберігайте один бізнес-ідентифікатор

Згенеруйте та збережіть `client_request_id`, перш ніж надсилати вилучення. Повторно використовуйте його для повторних спроб тієї ж запланованої операції, зокрема після перезапуску процесу. Зберігайте узгодженість полів транзакції; поточна реалізація відхиляє повторюваний ідентифікатор із суперечливими бізнес-параметрами.

Не покладайтеся лише на заголовок `Idempotency-Key`. Наданий SDK може додати цей заголовок, але поточний договір дедуплікації зняття коштів базується на полі тіла `client_request_id`.

<span id="understand-request-data" data-sixmm-canonical-anchor="understand-request-data" aria-hidden="true"></span>

## Розуміти дані запиту

| Поле | Значення |
| --- | --- |
| `chain_id`, `asset_id` | Ідентифікатори в узгодженому середовищі |
| `to_address`, `amount` | Призначення та позитивна десяткова сума, представлена ​​у вигляді рядка |
| `client_request_id` | Стабільний ідентифікатор бізнес-запиту |
| `dest_memo_type`, `dest_memo` | Деталі пам’ятки про призначення, якщо вони потрібні мережі |
| `client_authorization` | Авторизація транзчасток криптографічного ключа клієнта для зняття коштів, ініційованих API-ключем |
| `end_user_id` | Додатковий ідентифікатор бізнес-користувача в корпоративному потоці API. |

У цій таблиці виділено основні поля, а не повну схему запиту. Підтвердьте попередній перегляд, підтвердження комісії та спеціальні вимоги до зберігання щодо версії інтеграції. Уникайте двійкових значень із плаваючою комою та не копіюйте приклади ланцюжків чи номерів активів між середовищами.

<span id="follow-the-result" data-sixmm-canonical-anchor="follow-the-result" aria-hidden="true"></span>

## Слідкуйте за результатом

| Наведіть приклади | Інтерпретація |
| --- | --- |
| `pending_approval`, `pending_platform_review` | Схвалення або перевірка бізнесу не завершено |
| `approved`, `pending_sign` | Узгодження та підписання — окремі етапи |
| `broadcasting`, `pending_chain` | Триває трансляція або підтвердження ланцюжка |
| `broadcast_unverified`, `recovering` | Результат все ще невизначений; не створювати іншу передачу |
| `awaiting_reauthorization` | Для того самого запиту може знадобитися нова авторизація клієнта |
| `confirmed` | Система записала підтвердження ланцюга |

Список є ілюстративним і може доповнюватися. Зберігайте невідомі стани для дослідження замість того, щоб відображати їх успіх чи невдачу. Сама по собі невдала або відхилена мітка не є достатнім доказом того, що нічого не було підписано чи трансльовано.

<span id="recover-after-a-timeout" data-sixmm-canonical-anchor="recover-after-a-timeout" aria-hidden="true"></span>

## Відновити після тайм-ауту

Зробіть запит `GET /api/v1/withdrawals/by-request`, використовуючи оригінальний параметр запиту `client_request_id`. Продовжуйте опитування або узгодження початкової операції, поки її результат невизначений. Якщо потрібне поновлення авторизації, використовуйте той самий ідентифікатор і узгоджену процедуру поновлення.

Скасування залежить від фактичного етапу підписання та перевірок сервера. Розпочинайте бізнес-операцію заміни лише після того, як буде встановлено, що оригінал не переданий і неможливий для передачі. Отримувати події через [webhooks](/uk/mpc-wallet/webhooks-and-sdks)і збережіть API запити як шлях узгодження.
