Підготовка до безпеки починається з обрання домовленості про опіку. Захист облікового запису, схвалення транзчасток криптографічного ключа, MPC участь і матеріали для відновлення служать різним цілям.

<span id="assign-responsibilities" data-sixmm-canonical-anchor="assign-responsibilities" aria-hidden="true"></span>

## Розподіліть обов'язки

Окремий регулярний перегляд, ініціювання передачі, затвердження, адміністрування учасників і керування обліковими даними розробника, якщо продукт це дозволяє. Перевірте дозволи в призначеній робочій області; доступ до одного робочого простору не встановлює влади над іншим.

Для корпоративних робочих процесів узгодьте, хто переглядає зміни призначення та вихідні запити. Для підписання пристрою учасник повинен перевірити відображену мережу, актив, суму, призначення та контекст, перш ніж прийняти. Підтвердження пристрою не слід розглядати як запит на сліпе схвалення.

## Розрізняйте облікові дані

| матеріал | призначення |
| --- | --- |
| Автентифікація облікового запису | Доступ до програми користувача |
| API ключ і секрет | Автентифікуйте запити API. |
| Ключ авторизації клієнта | Авторизуйте вміст API зняття, якщо потрібно |
| MPC спільний ключ | Беріть участь у процесі розподіленого підпису гаманця |
| Матеріал резервного копіювання та відновлення | Відновіть участь або виконайте підтримувану процедуру відновлення |

Зберігайте їх відповідно до своїх обов’язків. Ключ API не є спільним доступом MPC; скидання пароля облікового запису не є операцією відновлення гаманця. Завантажуйте відкриті ключі лише через відповідний процес реєстрації, а не відповідні закриті ключі.

## Перед використанням підготуйте відновлення

Запишіть необхідних учасників, резервних власників і кроки відновлення під час реєстрації. Зберігайте резервні копії в окремих відповідних місцях і тестуйте підтримувану процедуру відновлення в контрольованому середовищі. Розглянемо як втрачений пристрій, так і збій служби платформи.

Самостійне зберігання ключів не дозволяє платформі відтворювати відсутні частки ключів клієнтів. Якщо залишиться занадто мало придатних для використання учасників і резервних копій, щоб задовольнити вимоги гаманця, доступ до активів може бути втрачено. Спільне зберігання ключів також потребує задокументованої плану відновлення; не припускайте, що участь у платформі гарантує відновлення.

## Обробка недоступного учасника

Спочатку розрізняйте тимчасову проблему підключення, недоступний пристрій і втрачений матеріал підпису. Перегляньте сеанс і стан пристрою, а потім скористайтеся підтримуваним процесом відновлення або заміни. Не стирайте пристрій, не змінюйте ідентифікатор підпису програми та не припускайте, що спільні ресурси можна перемістити, перш ніж перевірити вимоги відновлення.

Доступність резервної копії не є доказом завершення тесту відновлення. Перевірте, які процедури та інструменти включено у ваш випуск, перш ніж покладатися на них.
