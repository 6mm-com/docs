Є три окремі питання щодо підписання: автентифікація HTTP запиту, авторизація конкретного зняття коштів і створення підпису блокчейну з MPC учасниками. Проходження першої перевірки не замінює двох інших.

## Автентифікуйте API запит

Поточний API використовує HMAC-SHA256 з ідентифікатором ключа та секретом API. Його канонічний запит містить п’ять рядків, розділених символом нового рядка, без завершення нового рядка:

```text
METHOD
PATH
SORTED_QUERY
BODY_SHA256_HEX
UNIX_TIMESTAMP_SECONDS
```

Використовуйте метод HTTP у верхньому регістрі та шлях запиту без хосту. Сортуйте ключі запиту, зберігайте порядок повторюваних значень і застосовуйте кодування форми URL, включаючи `+` для пробілів. Рядок запиту порожній, якщо запиту немає. Хешуйте точні байти тіла за допомогою SHA-256, включаючи порожнє тіло для запиту без тіла.

Обчисліть HMAC-SHA256, використовуючи наданий секрет як UTF-8 байтів; не використовуйте шістнадцяткове кодування лише тому, що воно виглядає шістнадцятковим. Закодуйте результат як шістнадцятковий нижній регістр. Поля заголовка розділені пробілами:

```text
Authorization: HMAC-SHA256 keyId=<KEY_ID> signature=<HEX_SIGNATURE> timestamp=<UNIX_SECONDS>
```

## Приклад підпису лише для читання

Цей помічник стандартної бібліотеки створює заголовки для запиту депозиту; він не надсилає запит. Безпечно завантажте облікові дані у свою програму та надішліть повернутий шлях без змін до бази URL, наданої для вашого середовища.

```python
import hashlib
import hmac
import time
from urllib.parse import urlencode


def signed_read_headers(key_id, secret, timestamp=None):
    method = "GET"
    path = "/api/v1/deposits"
    query = urlencode(sorted([("page", "1"), ("page_size", "20")]))
    body = b""
    ts = str(int(time.time()) if timestamp is None else timestamp)
    canonical = "\n".join([
        method, path, query, hashlib.sha256(body).hexdigest(), ts
    ])
    signature = hmac.new(
        secret.encode("utf-8"), canonical.encode("utf-8"), hashlib.sha256
    ).hexdigest()
    return path + "?" + query, {
        "Authorization": (
            f"HMAC-SHA256 keyId={key_id} signature={signature} timestamp={ts}"
        )
    }
```

Тримайте годинник синхронізованим. Проксі-сервер, який змінює шлях, запит або тіло після підписання, може зробити автентифікацію недійсною. У разі помилок автентифікації перевірте причину відповіді та ідентифікатор запиту перед повторною спробою; ніколи не реєструйте секретний або повний заголовок авторизації.

## Авторизуйте API зняття

Поточний корпоративний процес зняття API також вимагає авторизації клієнта Ed25519 у `client_authorization`. Він прив’язує передбачуваний контекст транзакції, включаючи ідентифікатор запиту, призначення, актив і суму. Його реєстрація з відкритим ключем або конфігурація довіри залежать від домовленості про зберігання.

Використовуйте відповідний пакет інтеграції для створення канонічного корисного навантаження, підпису та відкритого ключа. Цей ключ авторизації окремий від спільних ресурсів HMAC та MPC. Зберігайте свій закритий ключ під контролем клієнта. Підтвердьте версію корисного навантаження та правила дійсності під час інтеграції замість того, щоб створювати спеціальний формат із цього огляду.

Після того, як запит прийнято, бізнес-перевірки та схвалення все ще можуть застосовуватися, а потім MPC підписання та ланцюжкове підтвердження. див [транзакції та повторні спроби](/uk/mpc-wallet/transactions).
