Цей посібник призначений для **Agent Java SDK `v0.3.0`** і Java 8+.

<span id="decide-what-needs-upgrading" data-sixmm-canonical-anchor="decide-what-needs-upgrading" aria-hidden="true"></span>

## Вирішіть, що потребує оновлення

| Існуюча інтеграція | Дія |
| --- | --- |
| Існуючі виробничі функції з пропущеним середовищем | Існуючі форми відповідей залишаються сумісними; нові запити не призводять до оновлення. |
| Існуюча загальна вбудована автентифікація для торгівлі секундами | Повторне використання автентифікації та оновлення; вибрати необхідну сторінку товару. |
| Залишки фінансування, перекази та повернення | Використовуйте моделі, що містять `withFunding`, `walletTransfer` і `queryWalletTransfer`. |
| Явні імітовані кошти | Використовуйте моделі запитів/відповідей, що підтримують `environment`. |
| Шість безперервних запитів даних | Використовуйте загальнодоступні Java SDK `v0.3.0`, включаючи шість методів і підтримку підпису масиву. |

Збережіть ваші поточні `baseUrl`, `agentCode`, `apiSecret`, прив’язки користувачів і оригінальні бізнес-замовлення.

## Встановіть стабільний публічний тег

Джерело хостів GitHub. Публікація тегу GitHub не публікує координати Maven у Maven Central. Установіть джерело з тегами локально або опублікуйте його перевірене JAR/POM у сховищі артефактів вашої організації.

```bash
git clone --branch v0.3.0 --single-branch https://github.com/6mm-com/agent-java-sdk.git agent-java-sdk-v0.3.0
cd agent-java-sdk-v0.3.0
git rev-parse HEAD
git rev-parse 'v0.3.0^{commit}'
mvn install
```

Два ідентифікатори фіксації мають збігатися. Оголосити залежність у партнерському проекті:

```xml
<dependency>
    <groupId>com.sixmm.exchange.sdk</groupId>
    <artifactId>agent</artifactId>
    <version>0.3.0</version>
</dependency>
```

Перевірте вирішену залежність:

```bash
mvn dependency:tree -Dincludes=com.sixmm.exchange.sdk:agent
```

Локальна інсталяція робить артефакт доступним лише на цій машині. CI та іншим розробникам потрібна така сама інсталяція з тегами або ваше перевірене сховище артефактів. Якщо у вас уже є приватний артефакт під назвою `0.3.0`, перевірте його джерело та методи; не перезаписуйте спільний артефакт автоматично.

<span id="required-integration-changes" data-sixmm-canonical-anchor="required-integration-changes" aria-hidden="true"></span>

## Необхідні зміни інтеграції

1. Оновити моделі запитів і відповідей для явного `environment`. Строгі старіші моделі відповідей можуть відхиляти додаткове поле.
2. Використовуйте `withFunding()` перед читанням `funding`. Контрактні баланси не є секундними торговими балансами.
3. Використовуйте `/v1/agent/wallet-transfer` і `/v1/agent/wallet-transfer-status` для фінансування. Старий `queryOrder` не може відновити операцію фінансування.
4. Шість запитів використовують `platformUserIds` як рядковий масив. Підпишіть масиви як компактні JSON; Java `List.toString()` несумісний.
5. Зберігайте замовлення на переказ, звичайні торгові замовлення, умовні замовлення та заповнення як окремі сутності. Проаналізуйте `orderStatus` або `status` відповідно до операції.
6. Перед синтаксичним аналізом перевірте вихідний текст webhook. Явні змодельовані сповіщення включають `environment`; порівняти його зі збереженим замовленням.
7. Незалежно керуйте версіями Java і Widget. Оновлення серверної частини не змінює зовнішню сторінку чи режим торгівлі, а для торгівлі секундами не потрібен новий тип маркера.

## Перевірте оновлення

Запустіть збірку партнерського проекту та перевірте його дерево залежностей. Тестове зв’язування, оригінальний виробничий потік, явні змодельовані баланси, відновлення результатів фінансування, усі шість запитів, фіксована розбивка вікон, обробка помилок та ідемпотентні зворотні виклики.

Для спеціального клієнта HTTP дотримуйтеся тегованого запиту та підпису контракту замість того, щоб припускати, що старі моделі охоплюють нові поля. див [Огляд запиту](/uk/sdk/agent-sdk/java/perpetual-queries) і [Керівництво по навколишньому середовищу](/uk/sdk/agent-sdk/java/environments).
