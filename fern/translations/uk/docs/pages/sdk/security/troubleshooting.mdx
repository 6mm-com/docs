Почніть з середовища, часової позначки та ідентифікатора бізнесу для невдалої операції. Структурована перевірка зазвичай розділяє проблеми конфігурації від аутентифікації, мережевої та асинхронної обробки.

<span id="diagnostic-order" data-sixmm-canonical-anchor="diagnostic-order" aria-hidden="true"></span>

## Рекомендований діагностичний порядок

1. Підтвердити уражене середовище та базову URL.
2. Запишіть UTC часовий діапазон і перший невдалий запит.
3. Визначте модуль: Trading Widget, Agent SDK, REST API, WebSocket, або webhook.
4. Зафіксуйте ідентифікатор запиту, ідентифікатор користувача партнера, `agentOrderNo`, ID замовлення або вебхук.
5. Перевірте останні зміни в коді, облікові дані, IP білий список або розгортання.
6. Відтворити з найменшим безпечним тестовим випадком.

<span id="trading-widget-issues" data-sixmm-canonical-anchor="trading-widget-issues" aria-hidden="true"></span>

## Trading Widget проблеми

| Симптоми | Ймовірна причина | Виправлення |
| --- | --- | --- |
| iframe запитує партнерський локальний домен | baseUrl відсутня | Передайте baseUrl: 'https://app.6mm.com'. |
| iframe невидимий або дуже короткий | Батьківський контейнер не має висоти | Встановіть висоту контейнера або висоту проходу. |
| token_provider_missing | Режим Partner-Token не має провайдера | Додайте автентифікаціюtokenProvider. |
| auth_exchange_failed | Недійсний, прострочений або невідповідний токен вбудови | Перевірте відповідь бекенд-токена та channelId. |

<span id="agent-sdk-issues" data-sixmm-canonical-anchor="agent-sdk-issues" aria-hidden="true"></span>

## Agent SDK проблеми

| Симптоми | Ймовірна причина | Виправлення |
| --- | --- | --- |
| Підпис відхилено | Неправильний секрет, зсув годинника або ручна зміна підписаних полів | Дозвольте SDK генерувати поля підписання та синхронізувати час сервера. |
| Ризик переміщення дублювання коштів | Новий номер замовлення використовується після тайм-ауту | Спочатку запит за оригінальним agentOrderNo . |
| PROCESSING вважали провалом | Неправильно зрозумілий стан очікування | Зачекайте на webhook або зателефонуйте queryOrder. |
| Вебхук оброблявся кілька разів | Спробуйте повторити поведінку без ідемпотентності | Додайте ключ ідемпотентності та перевірки фінального стану. |

## Докази для захоплення

| Інтеграція | Корисні докази |
| --- | --- |
| Trading Widget | Сторінка URL, SDK шлях версії, консоль браузера, невдалі мережеві запити, `onError` корисне навантаження та розміри контейнера. |
| Agent SDK | SDK мова/версія, базова URL, UTC часова мітка, ідентифікатор запиту, `agentOrderNo`, код відповіді та очищені журнали. |
| Webhook | Час доставки, ключ події або бізнесу, результат валідації підпису, стан обробки та очищений raw body хеш. |
| REST API | Метод, шлях, середовище, ідентифікатор запиту, код відповіді та прочистлені параметри. |

Ніколи не включайте паролі, токени доступу, API секрети, повні підписи, приватні ключі чи невідредаговані персональні дані в діагностиці.

<span id="before-escalating" data-sixmm-canonical-anchor="before-escalating" aria-hidden="true"></span>

## Перед ескалацією

- Спробуйте повторити лише тоді, коли операція задокументована як безпечна для повторної спроби.
- Після тайм-ауту запитуйте оригінальний бізнес-ідентифікатор замість створення нового.
- Підтвердити системний тактовий сигнал і середовище облікових даних на наявність помилок підпису.
- Зберегти першу невдачу та будь-які наступні результати повторних спроб.
- Використовуйте [Шаблон запиту підтримки](/uk/resources/support-request-template) для надсилання повного, відредагованого звіту.
