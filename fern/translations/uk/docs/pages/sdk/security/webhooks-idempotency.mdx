Webhooks сповіщати серверну частину партнера про асинхронні зміни бізнес-стану. Оскільки доставка може бути повторена, кожен одержувач повинен перевірити підпис перед аналізом довірених даних і повинен обробити подію ідемпотентно.

<span id="webhook-headers" data-sixmm-canonical-anchor="webhook-headers" aria-hidden="true"></span>

## Webhook заголовки

| Заголовок | опис |
| --- | --- |
| Мітка часу X-Agent | Позначка часу Unix у секундах. |
| X-Agent-Nonce | Захист від повтору одноразово. |
| X-Agent-Signature | HMAC-SHA256 підпис. |

```text
timestamp + nonce + rawBody
```

Використовуйте точне необроблене тіло запиту, отримане через HTTP під час реконструкції підписаного значення. Синтаксичний аналіз і повторна серіалізація JSON спочатку можуть змінити пробіли або ордер полів і створити інший підпис.

<span id="verification-flow" data-sixmm-canonical-anchor="verification-flow" aria-hidden="true"></span>

## Потік перевірки

1. Прочитайте заголовки позначки часу, одноразового використання та підпису.
2. Захоплення незміненого необробленого тіла запиту.
3. Збірка `timestamp + nonce + rawBody`.
4. Обчисліть HMAC-SHA256 із секретом партнера API.
5. Порівняйте розраховані та отримані підписи за допомогою порівняння в постійному часі.
6. Застосуйте схвалені перевірки актуальності позначок часу та повторного використання.
7. Проаналізуйте та обробіть подію лише після успішної перевірки.

Якщо доступний офіційний верифікатор Agent SDK, використовуйте його замість підтримки незалежного коду підпису.

<span id="order-idempotency" data-sixmm-canonical-anchor="order-idempotency" aria-hidden="true"></span>

## Ідемпотенція порядку

| Справа | поводження |
| --- | --- |
| Початковий запит на передачу | Створіть один глобально унікальний agentOrderNo. |
| HTTP час очікування | Запитайте оригінальний agentOrderNo перед створенням нового. |
| PROCESSING відповідь | Зачекайте на webhook або запит на статус замовлення. |
| Повторюється webhook | Дедуплікати за ключем ідемпотентності та кінцевим статусом. |

<span id="recommended-idempotency-record" data-sixmm-canonical-anchor="recommended-idempotency-record" aria-hidden="true"></span>

## Рекомендований запис ідемпотентності

Зберігайте достатньо інформації, щоб розпізнати повторне постачання та безпечно відновити:

| Поле | призначення |
| --- | --- |
| Подія або бізнес ключ | Унікально ідентифікує сповіщення або операцію. |
| Номер замовлення партнера | З’єднує подію з вихідним запитом. |
| Хеш корисного навантаження | Допомагає визначити конфліктні повторювані корисні навантаження. |
| Поточний стан обробки | Розрізняє отриману, оброблену, успішну та невдалу роботу. |
| Остаточний бізнес-статус | Запобігає подвійному застосуванню дії терміналу. |
| Опрацьована позначка часу | Підтримує політику розслідування та збереження. |

Зафіксуйте бізнес-зміни та запис ідемпотентності в одній транзакції, де це можливо. Повторювана подія має повернути вже відомий результат замість повторного застосування балансу, замовлення чи зміни користувача.

<span id="timeout-and-retry-rule" data-sixmm-canonical-anchor="timeout-and-retry-rule" aria-hidden="true"></span>

## Тайм-аут і правило повтору

Тайм-аут HTTP не доводить, що вихідний запит не виконано. Надішліть запит на операцію за допомогою оригінального `agentOrderNo` або зачекайте на його webhook, перш ніж вирішити, чи потрібна інша дія. Створення нового номеру бізнес-замовлення після кожного тайм-ауту може призвести до подвійних рухів коштів.

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## Контрольний лист виробництва

- Перевірте підпис перед синтаксичним аналізом JSON або бізнес-обробкою.
- Зберігайте необроблене тіло незалежно від проаналізованого корисного навантаження.
- Відхиляйте застарілі або повторно відтворені запити відповідно до затвердженої політики інтеграції.
- Зробіть обробку подій безпечною для повторної доставки та доставки поза замовленням.
- Реєструйте ідентифікатори подій, номери партнерських замовлень, результат обробки та час запиту.
- Видалення секретів і значень підпису з журналів і додатків підтримки.

## Межі фінансування та середовища

Оригінальний потік передачі Контракту webhook і `queryOrder` не застосовуються автоматично до Фінансування. Підтвердьте операції з фінансування за допомогою `queryWalletTransfer` і початкового середовища замовлення. Для фінансування використовується `status`; оригінальні відповіді щодо передачі контракту використовують `orderStatus`. Успішна HTTP відповідь або `code=0` сама по собі не підтверджує переміщення коштів.

Явні сповіщення про симуляцію передачі контракту включають `environment=SIMULATED`. Спочатку перевірте необроблене тіло, а потім порівняйте користувача, суму, ідентифікатор замовлення та середовище зі збереженим місцевим бізнес-замовленням.
