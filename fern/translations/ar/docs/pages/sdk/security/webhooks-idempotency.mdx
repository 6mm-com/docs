Webhooks قم بإخطار الواجهة الخلفية للشريك بشأن التغييرات غير المتزامنة في حالة العمل. ونظرًا لاحتمال إعادة محاولة التسليم، يجب على كل مستلم التحقق من التوقيع قبل تحليل البيانات الموثوقة ويجب معالجة الحدث بشكل غير فعال.

<span id="webhook-headers" data-sixmm-canonical-anchor="webhook-headers" aria-hidden="true"></span>

## Webhook رؤوس

| رأس | وصف |
| --- | --- |
| X-وكيل-الطابع الزمني | الطابع الزمني لنظام Unix بالثواني. |
| X-Agent-Nonce | إعادة الحماية nonce. |
| توقيع الوكيل X | HMAC-SHA256 التوقيع. |

```text
timestamp + nonce + rawBody
```

استخدم نص الطلب الأولي الدقيق المستلم عبر HTTP عند إعادة بناء القيمة الموقعة. يمكن أن يؤدي التحليل وإعادة التسلسل JSON أولاً إلى تغيير المسافة البيضاء أو ترتيب الحقل وإنتاج توقيع مختلف.

<span id="verification-flow" data-sixmm-canonical-anchor="verification-flow" aria-hidden="true"></span>

## تدفق التحقق

1. اقرأ الطابع الزمني والرقم ورؤوس التوقيع.
2. التقط نص الطلب الخام غير المعدل.
3. بناء `timestamp + nonce + rawBody`.
4. احسب HMAC-SHA256 مع الشريك السري API.
5. قارن التوقيعات المحسوبة والمستلمة باستخدام مقارنة الوقت الثابت.
6. قم بتطبيق عمليات التحقق من حداثة الطابع الزمني وعدم إعادة الاستخدام المعتمدة.
7. تحليل ومعالجة الحدث فقط بعد نجاح عملية التحقق.

عند توفر أداة التحقق الرسمية Agent SDK، استخدمها بدلاً من الاحتفاظ بكود توقيع مستقل.

<span id="order-idempotency" data-sixmm-canonical-anchor="order-idempotency" aria-hidden="true"></span>

## ترتيب العجز

| قضية | المناولة |
| --- | --- |
| طلب نقل مبدئي | قم بإنشاء واحدة فريدة عالميًا agentOrderNo. |
| HTTP المهلة | استعلم عن agentOrderNo الأصلي قبل إنشاء واحدة جديدة. |
| PROCESSING الرد | انتظر webhook أو الاستعلام عن حالة الطلب. |
| مكرر webhook | إلغاء التكرارات عن طريق مفتاح العجز والحالة النهائية. |

<span id="recommended-idempotency-record" data-sixmm-canonical-anchor="recommended-idempotency-record" aria-hidden="true"></span>

## أوصى سجل العجز

قم بتخزين معلومات كافية للتعرف على التسليم المتكرر واسترداده بأمان:

| مجال | غاية |
| --- | --- |
| الحدث أو مفتاح العمل | يحدد الإخطار أو العملية بشكل فريد. |
| رقم طلب الشريك | ربط الحدث بالطلب الأصلي. |
| تجزئة الحمولة | يساعد في تحديد الحمولات المتكررة المتعارضة. |
| حالة المعالجة الحالية | يميز بين الأعمال المستلمة والمعالجة والناجحة والفاشلة. |
| الوضع التجاري النهائي | يمنع تطبيق الإجراء النهائي مرتين. |
| الطابع الزمني المعالج | يدعم سياسات التحقيق والاحتفاظ. |

قم بإجراء سجل تغيير العمل والعجز في نفس المعاملة حيثما أمكن ذلك. يجب أن يؤدي الحدث المتكرر إلى إرجاع النتيجة المعروفة بالفعل بدلاً من تطبيق الرصيد أو الأمر أو تغيير المستخدم مرة أخرى.

<span id="timeout-and-retry-rule" data-sixmm-canonical-anchor="timeout-and-retry-rule" aria-hidden="true"></span>

## المهلة وإعادة المحاولة القاعدة

لا تثبت المهلة HTTP فشل الطلب الأصلي. استعلم عن العملية باستخدام `agentOrderNo` الأصلية، أو انتظر webhook، قبل أن تقرر ما إذا كان هناك حاجة إلى إجراء آخر. قد يؤدي إنشاء رقم أمر عمل جديد بعد كل مهلة إلى حدوث حركات مكررة للأموال.

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## قائمة مراجعة الإنتاج

- تحقق من التوقيع قبل تحليل JSON أو معالجة الأعمال.
- الحفاظ على الجسم الخام بشكل مستقل عن الحمولة التي تم تحليلها.
- رفض الطلبات القديمة أو المعاد تشغيلها وفقًا لسياسة التكامل المعتمدة.
- اجعل معالجة الأحداث آمنة للتسليم المتكرر والخارج عن الطلب.
- قم بتسجيل معرفات الأحداث وأرقام طلبات الشركاء ونتيجة المعالجة ووقت الطلب.
- تنقيح الأسرار وقيم التوقيع من السجلات ومرفقات الدعم.

## حدود التمويل والبيئة

لا يتم تطبيق تدفق نقل العقد الأصلي webhook و`queryOrder` تلقائيًا على التمويل. قم بتأكيد عمليات التمويل باستخدام `queryWalletTransfer` وبيئة الطلب الأصلية. استخدامات التمويل `status`؛ تستخدم ردود نقل العقد الأصلية `orderStatus`. إن الاستجابة الناجحة HTTP أو `code=0` لا تثبت في حد ذاتها نقل الأموال.

تتضمن إخطارات نقل العقد المحاكاة الصريحة `environment=SIMULATED`. تحقق من النص الخام أولاً، ثم تحقق من المستخدم والمبلغ وهوية الطلب والبيئة مقابل أمر العمل المحلي المحفوظ.
