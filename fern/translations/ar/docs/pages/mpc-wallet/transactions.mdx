السحب هو عملية تجارية غير متزامنة. الاستجابة الناجحة HTTP تعني أنه تم التعامل مع الطلب؛ ولا يثبت أن الأموال وصلت عبر السلسلة.

<span id="persist-one-business-identifier" data-sixmm-canonical-anchor="persist-one-business-identifier" aria-hidden="true"></span>

## استمر في معرف عمل واحد

قم بإنشاء وتخزين `client_request_id` قبل إرسال السحب. أعد استخدامه لإعادة محاولة نفس العملية المقصودة، بما في ذلك بعد إعادة تشغيل العملية. حافظ على اتساق حقول المعاملة؛ يرفض التنفيذ الحالي معرفًا متكررًا بمعلمات عمل متعارضة.

لا تعتمد فقط على رأس `Idempotency-Key`. يمكن أن يضيف SDK هذا الرأس، لكن عقد إلغاء البيانات المكررة للسحب الحالي يعتمد على حقل النص الأساسي `client_request_id`.

<span id="understand-request-data" data-sixmm-canonical-anchor="understand-request-data" aria-hidden="true"></span>

## فهم بيانات الطلب

| مجال | معنى |
| --- | --- |
| `chain_id`، `asset_id` | المعرفات في البيئة المتفق عليها |
| `to_address`، `amount` | الوجهة والمبلغ العشري الموجب الذي يتم تمثيله كسلسلة |
| `client_request_id` | معرف طلب عمل مستقر |
| `dest_memo_type`، `dest_memo` | تفاصيل مذكرة الوجهة حيث تتطلبها الشبكة |
| `client_authorization` | ترخيص معاملة العميل لـ API - عمليات السحب التي بدأت بالمفتاح |
| `end_user_id` | معرف مستخدم الأعمال الاختياري في تدفق المؤسسة API |

يسلط هذا الجدول الضوء على الحقول الأساسية، وليس مخطط الطلب الكامل. قم بتأكيد المعاينة وتأكيد الرسوم والمتطلبات الخاصة بالحفظ المفاتيح مقابل إصدار التكامل. تجنب المبالغ الثنائية الفاصلة العائمة ولا تنسخ سلسلة الأمثلة أو أرقام الأصول بين البيئات.

## اتبع النتيجة

| أمثلة الدولة | تفسير |
| --- | --- |
| `pending_approval`، `pending_platform_review` | موافقة العمل أو المراجعة رائعة |
| `approved`، `pending_sign` | الموافقة والتوقيع مرحلتان منفصلتان |
| `broadcasting`، `pending_chain` | جاري البث أو تأكيد السلسلة |
| `broadcast_unverified`، `recovering` | النتيجة لا تزال غير مؤكدة. لا تقم بإنشاء نقل آخر |
| `awaiting_reauthorization` | قد تكون هناك حاجة إلى تصريح عميل جديد لنفس الطلب |
| `confirmed` | قام النظام بتسجيل تأكيد السلسلة |

القائمة توضيحية وقد تتطور. الحفاظ على الحالات غير المعروفة للتحقيق فيها بدلاً من تعيينها للنجاح أو الفشل. التسمية الفاشلة أو المرفوضة وحدها لا تكفي دليلاً على عدم التوقيع أو البث.

## استرداد بعد مهلة

استعلم `GET /api/v1/withdrawals/by-request` باستخدام معلمة الاستعلام `client_request_id` الأصلية. استمر في الاقتراع أو التوفيق بين العملية الأصلية عندما تكون نتيجتها غير مؤكدة. إذا كان تجديد التفويض مطلوبًا، استخدم نفس المعرف وإجراءات التجديد المتفق عليها.

يعتمد الإلغاء على مرحلة التوقيع الفعلية وفحوصات الخادم. ابدأ عملية تجارية بديلة فقط بعد التأكد من عدم نقل الأصل وعدم إمكانية نقله. تلقي الأحداث من خلال [webhooks](/ar/mpc-wallet/webhooks-and-sdks)، والاحتفاظ بالاستعلامات API كمسار للتسوية.
