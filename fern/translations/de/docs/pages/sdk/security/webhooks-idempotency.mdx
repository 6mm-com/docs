Webhooks benachrichtigen ein Partner-Backend über asynchrone Änderungen des Geschäftsstatus. Da die Zustellung wiederholt werden kann, muss jeder Empfänger die Signatur überprüfen, bevor er vertrauenswürdige Daten analysiert, und das Ereignis idempotent verarbeiten.

<span id="webhook-headers" data-sixmm-canonical-anchor="webhook-headers" aria-hidden="true"></span>

## Webhook-Header

| Kopfzeile | Beschreibung |
| --- | --- |
| X-Agent-Zeitstempel | Unix-Zeitstempel in Sekunden. |
| X-Agent-Nonce | Wiedergabeschutz-Nonce. |
| X-Agent-Signatur | HMAC-SHA256 Signatur. |

```text
timestamp + nonce + rawBody
```

Verwenden Sie bei der Rekonstruktion des vorzeichenbehafteten Werts den genauen rohen Anforderungstext, der über HTTP empfangen wurde. Das erste Parsen und erneute Serialisieren von JSON kann die Leerzeichen- oder Feldreihenfolge ändern und eine andere Signatur erzeugen.

<span id="verification-flow" data-sixmm-canonical-anchor="verification-flow" aria-hidden="true"></span>

## Verifizierungsablauf

1. Lesen Sie die Zeitstempel-, Nonce- und Signatur-Header.
2. Erfassen Sie den unveränderten rohen Anforderungstext.
3. Erstellen Sie `timestamp + nonce + rawBody`.
4. Berechnen Sie HMAC-SHA256 mit dem Partner-Geheimnis API.
5. Vergleichen Sie die berechneten und empfangenen Signaturen mithilfe eines zeitkonstanten Vergleichs.
6. Wenden Sie die genehmigten Zeitstempelaktualisierungs- und Nonce-Wiederverwendungsprüfungen an.
7. Analysieren und verarbeiten Sie das Ereignis erst, nachdem die Überprüfung erfolgreich war.

Wenn ein offizieller Prüfer Agent SDK verfügbar ist, verwenden Sie ihn, anstatt einen unabhängigen Signaturcode zu verwalten.

<span id="order-idempotency" data-sixmm-canonical-anchor="order-idempotency" aria-hidden="true"></span>

## Orderen Sie Idempotenz

| Fall | Handhabung |
| --- | --- |
| Erster Transferantrag | Erstellen Sie ein weltweit eindeutiges agentOrderNo. |
| HTTP Zeitüberschreitung | Fragen Sie den ursprünglichen agentOrderNo ab, bevor Sie einen neuen erstellen. |
| PROCESSING Antwort | Warten Sie auf webhook oder fragen Sie den Orderstatus ab. |
| Wiederholt webhook | Deduplizieren nach Idempotenzschlüssel und Endstatus. |

<span id="recommended-idempotency-record" data-sixmm-canonical-anchor="recommended-idempotency-record" aria-hidden="true"></span>

## Empfohlener Idempotenz-Datensatz

Speichern Sie genügend Informationen, um eine wiederholte Zustellung zu erkennen und sicher wiederherzustellen:

| Feld | Zweck |
| --- | --- |
| Ereigniss- oder Geschäftsschlüssel | Identifiziert die Benachrichtigung oder den Vorgang eindeutig. |
| Ordernummer des Partners | Verbindet das Ereignis mit der ursprünglichen Anfrage. |
| Nutzlast-Hash | Hilft bei der Identifizierung widersprüchlicher wiederholter Nutzlasten. |
| Aktueller Bearbeitungsstand | Unterscheidet zwischen empfangener, verarbeiteter, erfolgreicher und fehlgeschlagener Arbeit. |
| Endgültiger Geschäftsstatus | Verhindert, dass eine Terminalaktion zweimal angewendet wird. |
| Verarbeiteter Zeitstempel | Unterstützt Untersuchungs- und Aufbewahrungsrichtlinien. |

Übernehmen Sie die Geschäftsänderung und den Idempotenzdatensatz nach Möglichkeit in derselben Transaktion. Ein wiederholtes Ereignis sollte das bereits bekannte Ergebnis zurückgeben, anstatt den Kontostand, die Order oder die Benutzeränderung erneut anzuwenden.

<span id="timeout-and-retry-rule" data-sixmm-canonical-anchor="timeout-and-retry-rule" aria-hidden="true"></span>

## Timeout- und Wiederholungsregel

Eine HTTP-Zeitüberschreitung beweist nicht, dass die ursprüngliche Anfrage fehlgeschlagen ist. Fragen Sie den Vorgang mit dem ursprünglichen `agentOrderNo` ab oder warten Sie auf dessen webhook, bevor Sie entscheiden, ob eine weitere Aktion erforderlich ist. Das Erstellen einer neuen Geschäftsauftragsnummer nach jeder Zeitüberschreitung kann zu doppelten Geldbewegungen führen.

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## Checkliste für die Produktion

- Überprüfen Sie vorher die Signatur JSON Parsing oder Geschäftsverarbeitung.
- Bewahren Sie den Rohkörper unabhängig von der analysierten Nutzlast auf.
- Lehnen Sie veraltete oder wiederholte Anfragen gemäß der genehmigten Integrationsrichtlinie ab.
- Machen Sie die Ereignisverarbeitung für wiederholte und nicht ordnungsgemäße Zustellung sicher.
- Protokollieren Sie Ereignis-IDs, Partnerbestellnummern, Verarbeitungsergebnis und Anfragezeit.
- Schwärzen Sie Geheimnisse und Signaturwerte aus Protokollen und Support-Anhängen.

## Finanzierungs- und Umweltgrenzen

Die ursprünglichen Vertragsübertragungsabläufe webhook und `queryOrder` gelten nicht automatisch für die Finanzierung. Bestätigen Sie Finanzierungsvorgänge mit `queryWalletTransfer` und der ursprünglichen Orderumgebung. Finanzierungsverwendungen `status`; Ursprüngliche Vertragsübertragungsantworten verwenden `orderStatus`. Eine erfolgreiche HTTP-Antwort oder `code=0` allein beweist nicht, dass Gelder bewegt wurden.

Zu den expliziten simulierten Vertragsübertragungsbenachrichtigungen gehören `environment=SIMULATED`. Überprüfen Sie zuerst den Rohkörper und vergleichen Sie dann den Benutzer, den Betrag, die Orderidentität und die Umgebung mit der gespeicherten lokalen GeschäftsOrder.
