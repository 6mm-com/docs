Agent SDK-Anfragen werden mit einem Partner-API-Geheimnis authentifiziert. Bewahren Sie dieses Geheimnis in einem vertrauenswürdigen Backend-Dienst auf und lassen Sie SDK wann immer möglich Signaturfelder generieren.

> **Zwei Signaturprotokolle**
>
> Beim Signieren mit Agent SDK werden sortierte Anforderungsfelder, ein sekundenbasierter Zeitstempel und eine Nonce verwendet. Direkte Developer API-Anfragen verwenden den separaten Prozess, der in beschrieben wird [Signieren anfordern](/de/developer-api/request-signing). Verwenden Sie nicht ein Nutzlastformat für ein anderes.

<span id="signing-rule" data-sixmm-canonical-anchor="signing-rule" aria-hidden="true"></span>

## Unterzeichnungsregel

Für Agent SDK-Anfragen:

1. Schließen Sie das Feld `sign` aus.
2. Lassen Sie Felder mit leeren Werten weg.
3. Sortieren Sie die verbleibenden Feldnamen in der Reihenfolge ASCII.
4. Verknüpfen Sie die Felder als `k=v&k2=v2`.
5. Berechnen Sie die hexadezimale Signatur HMAC-SHA256 mit `apiSecret`.

Array-Werte werden als kompakte JSON serialisiert, bevor sie der Signierungsnutzlast hinzugefügt werden. Beispielsweise signiert `platformUserIds` als `["1188041528"]` und ergibt `platformUserIds=["1188041528"]` in der Nutzlast `k=v`. Behalten Sie die Reihenfolge der Array-Elemente, doppelte Anführungszeichen und String-IDs bei. Fügen Sie keine Formatierungsleerzeichen ein und verwenden Sie nicht Java `List.toString()` (z. B. `[1188041528]`). Der SDK übernimmt diese Serialisierung automatisch.

Der SDK sollte diesen Wert aus denselben Daten erstellen, die er sendet. Das Ändern eines signierten Felds nach der Signaturgenerierung führt dazu, dass die Überprüfung fehlschlägt.

<span id="sdk-managed-fields" data-sixmm-canonical-anchor="sdk-managed-fields" aria-hidden="true"></span>

## SDK-verwaltete Felder

| Feld | Quelle | Beschreibung |
| --- | --- | --- |
| agentCode | SDK Konfig | Code des Partneragenten. |
| Zeitstempel | Aktuelle Serverzeit | Unix-Zeitstempel in Sekunden. |
| einmal | Sicherer Zufallswert | Zufallszeichenfolge zum Schutz vor Wiedergabe. |
| Zeichen | HMAC-SHA256 | Unterschrift anfordern. |
| Währung | Standardwährung | Wird verwendet, wenn bei Überweisung/Konto APIs die Währung weggelassen wird. |

<span id="secret-storage" data-sixmm-canonical-anchor="secret-storage" aria-hidden="true"></span>

## Geheimspeicher

- Laden Sie `apiSecret` von einem Backend-Secret-Manager oder einer geschützten Laufzeitkonfiguration.
- Platzieren Sie das Geheimnis niemals in Frontend-Paketen, mobilen Apps, Desktop-Clients, Screenshots oder Support-Tickets.
- Halten Sie die Anmeldeinformationen für Entwicklung, Staging und Produktion getrennt.
- Beschränken Sie den Zugriff auf die Dienste und Betreiber, die dies erfordern.
- Schwärzen Sie Anforderungssignaturen, Autorisierungswerte und Geheimnisse aus Protokollen.
- Widerrufen und ersetzen Sie Anmeldeinformationen, wenn der Verdacht besteht, dass Sie gefährdet sind.

<span id="clock-and-replay-protection" data-sixmm-canonical-anchor="clock-and-replay-protection" aria-hidden="true"></span>

## Takt- und Wiedergabeschutz

Das SDK umfasst `timestamp` und `nonce`, um das Wiederholungsrisiko zu verringern. Halten Sie die Backend-Uhren synchronisiert und verwenden Sie keine manuell erstellte Nonce wieder. Wenn die Signaturvalidierung fehlschlägt, überprüfen Sie das konfigurierte Geheimnis, die Serverzeit, die serialisierten Felder und die Umgebung, bevor Sie es erneut versuchen.

<span id="integration-checklist" data-sixmm-canonical-anchor="integration-checklist" aria-hidden="true"></span>

## Checkliste zur Integration

| Überprüfen | Erwartetes Ergebnis |
| --- | --- |
| Geheimer Ort | Nur Backend-geheimer Speicher. |
| Umfeld | Basis URL und Anmeldeinformationen gehören zur selben Umgebung. |
| Feldhandhabung | SDK generiert `timestamp`, `nonce` und `sign`. |
| Protokollierung | Geschäfts-IDs bleiben sichtbar, während Anmeldeinformationen geschwärzt werden. |
| Drehung | Berechtigungsnachweisinhaber und Austauschprozess werden dokumentiert. |
