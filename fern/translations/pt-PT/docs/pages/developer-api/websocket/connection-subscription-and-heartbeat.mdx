Use WebSocket fluxos para dados de mercado e atualizações privadas do estado dos utilizadores que devem manter-se atualizadas sem necessidade de sondagens.

<span id="connection-url" data-sixmm-canonical-anchor="connection-url" aria-hidden="true"></span>

## Ligação URL

```text
wss://ws.6mm.com/ws
```

Os fluxos privados requerem contexto de autenticação, como um listenKey ou token de acesso, conforme descrito na documentação do canal privado.

<span id="subscribe" data-sixmm-canonical-anchor="subscribe" aria-hidden="true"></span>

## Subscreva

```json
{ "id": "1772007814666", "op": "subscribe", "args": ["market.depth.BTCUSDT"] }
```

Reconhecimento de subscrição bem-sucedida:

```json
{
  "id": "1772007814666",
  "event": "subscribe",
  "success": true,
  "data": ["market.depth.BTCUSDT"]
}
```

<span id="unsubscribe" data-sixmm-canonical-anchor="unsubscribe" aria-hidden="true"></span>

## Desassinar

```json
{ "id": "1772007814667", "op": "unsubscribe", "args": ["market.depth.BTCUSDT"] }
```

<span id="application-ping" data-sixmm-canonical-anchor="application-ping" aria-hidden="true"></span>

## Ping da aplicação

```json
{ "id": "1772007814668", "op": "ping", "args": [] }
```

<span id="message-envelope" data-sixmm-canonical-anchor="message-envelope" aria-hidden="true"></span>

## Envelope de mensagens

As campanhas públicas usam um envelope consistente:

```json
{
  "topic": "market.depth.BTCUSDT",
  "event": "data",
  "ts": 1772007815000,
  "data": {}
}
```

<span id="operational-recommendations" data-sixmm-canonical-anchor="operational-recommendations" aria-hidden="true"></span>

## Recomendações operacionais

- Gerar uma `id` única do lado do cliente para cada pedido de subscrição, cancelamento e ping.
- Tratar a reconexão como uma nova sessão e subscrever novamente os tópicos exigidos.
- Validar se o `topic` devolvido corresponde ao canal que o seu serviço espera.
- Manter o processamento de mensagens idempotente quando estão envolvidos eventos privados de ordem ou de conta.
- Alterações ao estado da ligação no registo, confirmações de subscrição e desconexões anormais.

<span id="reconnect-workflow" data-sixmm-canonical-anchor="reconnect-workflow" aria-hidden="true"></span>

## Fluxo de trabalho de reconexão

1. Feche ou descarte o soquete anterior e crie uma nova ligação.
2. Re-autenticar fluxos privados com um listenKey ou token de acesso válido.
3. Volte a subscrever todos os tópicos exigidos e aguarde por reconhecimentos bem-sucedidos.
4. Substituir o estado local do livro de ordens por um novo snapshot antes de aplicar atualizações incrementais.
5. Reconciliar ordens abertas, posições e saldos através da REST caso eventos privados possam ter sido perdidos.

Usa backoff exponencial limitado com jitter para tentativas de religação. Um cliente que se reconecta continuamente deve alertar os operadores em vez de tentar indefinidamente sem visibilidade.

<span id="heartbeat-and-stale-connections" data-sixmm-canonical-anchor="heartbeat-and-stale-connections" aria-hidden="true"></span>

## Batimentos cardíacos e ligações estagnadas

- Rastrear a mensagem de entrada mais recente e o reconhecimento de ping bem-sucedido.
- Utilizar o intervalo de batimentos cardíacos e o limiar de repouso aprovados para o ambiente de produção.
- Tratar uma ligação como obsoleta quando o limiar configurado é ultrapassado, mesmo que o soquete TCP ainda pareça aberto.
- Não reutilizar subscrições de um socket antigo; Volte a subscrever explicitamente após cada reconexão.
