보안 준비는 선택한 키 보관 계약부터 시작됩니다. 계정 보호, 거래 승인, MPC 참여 및 복구 자료는 다양한 목적으로 사용됩니다.

<span id="assign-responsibilities" data-sixmm-canonical-anchor="assign-responsibilities" aria-hidden="true"></span>

## 책임 할당

제품에서 허용하는 경우 일상적인 조회, 전송 개시, 승인, 회원 관리 및 개발자 자격 증명 관리를 별도로 수행합니다. 의도한 작업공간에서 권한을 확인하세요. 한 작업공간에 대한 액세스가 다른 작업공간에 대한 권한을 설정하지 않습니다.

엔터프라이즈 워크플로의 경우 대상 변경 사항 및 발신 요청을 검토하는 사람에 동의합니다. 장치 서명의 경우 참가자는 수락하기 전에 표시된 네트워크, 자산, 금액, 대상 및 컨텍스트를 검사해야 합니다. 장치 확인을 블라인드 승인 프롬프트로 취급해서는 안 됩니다.

<span id="keep-credentials-distinct" data-sixmm-canonical-anchor="keep-credentials-distinct" aria-hidden="true"></span>

## 자격 증명을 구별되게 유지

| 재료 | 목적 |
| --- | --- |
| 계정 인증 | 사용자 애플리케이션에 액세스 |
| API 키와 비밀 | 백엔드 API 요청 인증 |
| 고객 인증 키 | 필요한 경우 API 철회 내용을 승인합니다. |
| MPC 키 공유 | 지갑의 분산 서명 프로세스에 참여 |
| 백업 및 복구 자료 | 참여를 복원하거나 지원되는 복구 절차를 수행합니다. |

각자의 책임에 따라 보관하세요. API 키는 MPC 공유가 아닙니다. 계정 비밀번호 재설정은 지갑 복구 작업이 아닙니다. 공개 키는 관련 등록 흐름을 통해서만 업로드하고 해당 개인 키는 업로드하지 마세요.

## 사용 전 복구 준비

온보딩 중에 필요한 참가자, 백업 소유자 및 복구 단계를 기록합니다. 별도의 적절한 위치에 백업을 보관하고 통제된 환경에서 지원되는 복구 절차를 테스트하십시오. 분실된 장치와 플랫폼 서비스 중단을 모두 고려하십시오.

자체 보관은 플랫폼이 누락된 고객 지분을 다시 생성하는 것을 허용하지 않습니다. 지갑의 요구 사항을 충족하기 위해 사용 가능한 참가자와 백업이 너무 적으면 자산에 대한 액세스가 손실될 수 있습니다. 공동 키 보관에는 문서화된 회복 합의도 필요합니다. 플랫폼 참여가 회복을 보장한다고 가정하지 마십시오.

<span id="handle-an-unavailable-participant" data-sixmm-canonical-anchor="handle-an-unavailable-participant" aria-hidden="true"></span>

## 사용할 수 없는 참가자 처리

먼저 일시적인 연결 문제, 사용할 수 없는 장치 및 서명 자료 분실을 구별하십시오. 세션 및 장치 상태를 검토한 다음 지원되는 복구 또는 교체 프로세스를 사용하십시오. 복구 요구 사항을 확인하기 전에 장치를 지우거나 응용 프로그램 서명 ID를 변경하거나 공유를 이동할 수 있다고 가정하지 마십시오.

백업 가용성은 복구 테스트가 완료되었다는 증거가 아닙니다. 사용하기 전에 릴리스에 어떤 절차와 도구가 포함되어 있는지 확인하세요.
