실패한 작업의 환경, 타임스탬프, 비즈니스 식별자부터 시작하세요. 구조화된 검사는 보통 구성 문제와 인증, 네트워크, 비동기 처리 문제를 분리합니다.

<h2 id="diagnostic-order">권장 진단 순서</h2>

1. 영향을 받은 환경과 기본 URL 확인.
2. UTC 시간 범위와 첫 번째 실패 요청을 기록합니다.
3. 모듈을 식별합니다: Trading Widget, Agent SDK, REST API, WebSocket, 또는 webhook.
4. 요청 ID, 파트너 사용자 ID, `agentOrderNo`, 주문 ID, webhook 이벤트 ID를 캡처합니다.
5. 최근 코드, 자격 증명, IP 화이트리스트 또는 배포 변경 사항을 확인하세요.
6. 가장 작은 안전한 테스트 케이스로 번식한다.

<h2 id="trading-widget-issues">Trading Widget 문제점</h2>

| 증상 | 원인 중 유력한 | 수정 |
| --- | --- | --- |
| iFrame이 파트너 로컬 도메인을 요청합니다 | baseUrl 없어졌어 | 패스 baseUrl: 'https://app.6mm.com'. |
| 아이프레임은 보이지 않거나 매우 짧습니다 | 부모 컨테이너는 높이가 없습니다 | 용기 높이나 패스 높이를 설정하세요. |
| token_provider_missing | 파트너 토큰 모드에는 제공자가 없습니다 | 권한을 추가하세요.tokenProvider. |
| auth_exchange_failed | 유효하지 않거나, 만료되었거나, 맞지 않는 임베드 토큰 | 백엔드 토큰 응답과 channelId확인해 보세요. |

<h2 id="agent-sdk-issues">Agent SDK 문제점</h2>

| 증상 | 원인 중 유력한 | 수정 |
| --- | --- | --- |
| 서명 거부됨 | 잘못된 비밀, 시계 지연, 또는 수동으로 서명된 필드를 변경한 경우입니다 | 서명 필드를 생성하고 서버 시간을 동기화하는 SDK |
| 중복 자금 이동 위험 | 타임아웃 후 새 주문 번호 사용 | 먼저 원본 agentOrderNo 로 쿼리하세요. |
| PROCESSING 실패로 취급받는다 | 대기 중인 주 오해가 | webhook 기다리거나 queryOrder에게 전화하세요. |
| Webhook 여러 번 처리되었습니다 | 놔등성 없는 재시도 행동 | 딙등성 키와 최종 상태 검사를 추가하세요. |

<h2 id="evidence-to-capture">증거 수집</h2>

| 통합 | 유용한 증거 |
| --- | --- |
| Trading Widget | 페이지 URL, SDK 버전 경로, 브라우저 콘솔, 실패한 네트워크 요청, `onError` 페이로드, 컨테이너 크기 등이 포함됩니다. |
| Agent SDK | SDK 언어/버전, 기본 URL, UTC 타임스탬프, 요청 ID, `agentOrderNo`, 응답 코드, 그리고 정제된 로그를 포함합니다. |
| Webhook | 전달 시간, 이벤트 또는 비즈니스 키, 서명 검증 결과, 처리 상태, 그리고 정제된 원시 해시. |
| REST API | 메서드, 경로, 환경, 요청 ID, 응답 코드, 그리고 정제된 매개변수. |

진단 검사에 비밀번호, 접근 토큰, API 비밀, 완전한 서명, 개인 키, 또는 편집되지 않은 개인 데이터를 절대 포함하지 마세요.

<h2 id="before-escalating">상황을 악화시키기 전</h2>

- 작업이 안전하다고 문서화되어 있을 때만 재시도합니다.
- 타임아웃 후에는 새 식별자를 생성하지 않고 원래 비즈니스 식별자를 쿼리합니다.
- 시스템 클럭 및 자격 증명 환경에서 서명 오류를 확인한다.
- 첫 번째 실패와 이후 재시도 결과를 보존합니다.
- 다음 [지원 요청 템플릿](/ko/resources/support-request-template) 완전하고 검열된 보고서를 보내기 위해서였다.
