Webhooks 비동기 비즈니스 상태 변경에 대해 파트너 백엔드에 알립니다. 전달이 재시도될 수 있으므로 모든 수신자는 신뢰할 수 있는 데이터를 구문 분석하기 전에 서명을 확인해야 하며 이벤트를 멱등적으로 처리해야 합니다.

<span id="webhook-headers" data-sixmm-canonical-anchor="webhook-headers" aria-hidden="true"></span>

## Webhook 헤더

| 헤더 | 설명 |
| --- | --- |
| X-에이전트-타임스탬프 | 초 단위의 Unix 타임스탬프입니다. |
| X-에이전트-Nonce | 재생 보호 임시값. |
| X-에이전트 서명 | HMAC-SHA256 서명. |

```text
timestamp + nonce + rawBody
```

서명된 값을 재구성할 때 HTTP을 통해 수신된 정확한 원시 요청 본문을 사용하세요. JSON을 먼저 구문 분석하고 다시 직렬화하면 공백이나 필드 순서가 변경되어 다른 서명이 생성될 수 있습니다.

<span id="verification-flow" data-sixmm-canonical-anchor="verification-flow" aria-hidden="true"></span>

## 확인 흐름

1. 타임스탬프, nonce 및 서명 헤더를 읽습니다.
2. 수정되지 않은 원시 요청 본문을 캡처합니다.
3. `timestamp + nonce + rawBody`를 빌드합니다.
4. 파트너 API 비밀을 사용하여 HMAC-SHA256를 계산합니다.
5. 상수 시간 비교를 사용하여 계산된 서명과 수신된 서명을 비교합니다.
6. 승인된 타임스탬프 최신성 및 임시 재사용 검사를 적용합니다.
7. 확인이 성공한 후에만 이벤트를 구문 분석하고 처리합니다.

공식 Agent SDK 검증자를 사용할 수 있는 경우 독립적인 서명 코드를 유지하는 대신 이를 사용하세요.

## 멱등성 주문

| 사례 | 손질 |
| --- | --- |
| 최초 이체 요청 | 전역적으로 고유한 agentOrderNo 하나를 만듭니다. |
| HTTP 시간 초과 | 새 항목을 만들기 전에 원본 agentOrderNo을 쿼리하세요. |
| PROCESSING 응답 | webhook을 기다리거나 주문 상태를 문의하세요. |
| 반복 webhook | 멱등성 키 및 최종 상태를 기준으로 중복을 제거합니다. |

<span id="recommended-idempotency-record" data-sixmm-canonical-anchor="recommended-idempotency-record" aria-hidden="true"></span>

## 권장 멱등성 레코드

반복적인 전달을 인식하고 안전하게 복구할 수 있도록 충분한 정보를 저장하세요.

| 필드 | 목적 |
| --- | --- |
| 이벤트 또는 비즈니스 키 | 알림 또는 작업을 고유하게 식별합니다. |
| 파트너 주문 번호 | 이벤트를 원래 요청에 연결합니다. |
| 페이로드 해시 | 충돌하는 반복 페이로드를 식별하는 데 도움이 됩니다. |
| 현재 처리 상태 | 수신, 처리, 성공, 실패한 작업을 구분합니다. |
| 최종 사업현황 | 터미널 작업이 두 번 적용되는 것을 방지합니다. |
| 처리된 타임스탬프 | 조사 및 보존 정책을 지원합니다. |

가능한 경우 동일한 트랜잭션에서 비즈니스 변경 및 멱등성 레코드를 커밋합니다. 반복되는 이벤트는 잔액, 주문 또는 사용자 변경 사항을 다시 적용하는 대신 이미 알려진 결과를 반환해야 합니다.

<span id="timeout-and-retry-rule" data-sixmm-canonical-anchor="timeout-and-retry-rule" aria-hidden="true"></span>

## 시간 초과 및 재시도 규칙

HTTP 시간 초과는 원래 요청이 실패했음을 증명하지 않습니다. 다른 작업이 필요한지 결정하기 전에 원본 `agentOrderNo`을 사용하여 작업을 쿼리하거나 webhook을 기다립니다. 시간이 초과될 때마다 새 비즈니스 주문 번호를 생성하면 자금 이동이 중복될 수 있습니다.

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## 생산 체크리스트

- JSON 구문 분석 또는 비즈니스 처리 전에 서명을 확인하세요.
- 구문 분석된 페이로드와 별도로 원시 본문을 보존합니다.
- 승인된 통합 정책에 따라 오래되거나 재생된 요청을 거부합니다.
- 반복적이고 잘못된 전달에 대해 이벤트 처리를 안전하게 만듭니다.
- 이벤트 ID, 파트너 주문 번호, 처리 결과, 요청 시간을 기록합니다.
- 로그 및 지원 첨부 파일에서 비밀과 서명 값을 수정합니다.

## 자금 및 환경 경계

원래 계약 이전 webhook 및 `queryOrder` 흐름은 자금 조달에 자동으로 적용되지 않습니다. `queryWalletTransfer` 및 원래 주문 환경을 사용하여 자금 조달 작업을 확인합니다. 자금은 `status`를 사용합니다. 원래 계약 이전 응답은 `orderStatus`를 사용합니다. 성공적인 HTTP 응답 또는 `code=0` 자체만으로는 자금이 이동되었음을 증명하지 않습니다.

명시적인 시뮬레이션 계약 이전 알림에는 `environment=SIMULATED`이 포함됩니다. 원시 본문을 먼저 확인한 다음 저장된 로컬 비즈니스 주문을 기준으로 사용자, 금액, 주문 ID 및 환경을 확인합니다.
