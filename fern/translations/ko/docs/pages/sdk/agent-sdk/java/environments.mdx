이 가이드는 **Agent Java SDK `v0.3.0`** 및 Java 8+를 대상으로 합니다.

<span id="choose-both-the-frontend-mode-and-the-funds-environment" data-sixmm-canonical-anchor="choose-both-the-frontend-mode-and-the-funds-environment" aria-hidden="true"></span>

## 프론트엔드 모드와 자금 환경을 모두 선택하세요

프런트엔드 거래 모드와 별도로 파트너 백엔드의 자금 환경을 구성합니다. 바인딩 및 항목 자격 증명은 공유됩니다. 티켓이나 토큰을 발행한다고 해서 지갑을 선택하거나 자금을 이동하는 것은 아닙니다.

| 구성 | 생산 | 시뮬레이션 |
| --- | --- | --- |
| 바인딩 및 인증 | 공유 사용자 바인딩 및 일회성 자격 증명 | 동일한 신원 및 인증 |
| 새로운 전송 및 사용자 잔액 | `environment`를 생략하거나 `PRODUCTION`를 사용하세요. | `SIMULATED`를 명시적으로 사용하세요. |
| 원래 주문 복구 자금 조달 | 저장된 원본 환경을 사용하세요 | 저장된 원본 환경을 사용하세요 |
| 위젯 거래 모드 | `tradingMode=real` | `tradingMode=demo` |
| 프런트엔드 HTTP/WS 대상 | 6MM에서 공급하는 생산 목표 | 6MM에서 제공하는 시뮬레이션 대상 |
| 6개의 영구 데이터 쿼리 | 생산 데이터 | 환경 선택기가 없습니다. 이러한 메서드는 시뮬레이션된 데이터를 쿼리하지 않습니다. |

`wallet-transfer-status`의 경우 `environment`를 생략하면 시뮬레이션된 주문을 포함하여 원래 주문의 저장된 환경이 사용됩니다. 명시적으로 충돌하는 환경은 거부됩니다. 작업을 복구할 때 환경을 저장하고 명시적으로 전달하는 것을 선호합니다.

`isSimulatedUser`은 계정을 설명합니다. 새 요청을 시뮬레이션된 지갑으로 라우팅하지 않습니다. 새 자금 요청에서 `environment`를 생략하면 계정 플래그가 true인 경우에도 여전히 생산이 선택됩니다.

<span id="supported-java-request-models" data-sixmm-canonical-anchor="supported-java-request-models" aria-hidden="true"></span>

## 지원되는 Java 요청 모델

이러한 요청은 `withEnvironment(ExecutionEnvironment.SIMULATED)`를 지원합니다.

- `TransferRequest`, `TransferAllOutRequest`, `ReverseOrderRequest`.
- `QueryOrderRequest`, `ListOrdersRequest`.
- `QueryUserAssetsRequest`.
- `WalletTransferRequest`, `WalletTransferQueryRequest`.

`bind`, `queryAccount`, `createEntryUrl`, `createEmbedToken` 및 6개의 영구 쿼리 요청 모델은 자금 환경을 선택하지 않습니다.

```java
import com.sixmm.agent.model.ExecutionEnvironment;
import com.sixmm.agent.model.QueryUserAssetsRequest;
import com.sixmm.agent.model.QueryUserAssetsResponse;

QueryUserAssetsResponse assets = client.queryUserAssets(
        QueryUserAssetsRequest.of("1188041528")
                .withFunding()
                .withEnvironment(ExecutionEnvironment.SIMULATED));
```

다음을 사용하여 `client`를 초기화합니다. [빠른 시작](/ko/sdk/agent-sdk/java/quick-start) 저장된 바인딩의 공용 사용자 ID를 사용하세요.

## 원래의 환경을 보존하세요

자금 요청을 보내기 전에 인터페이스 유형, `agentOrderNo`, 사용자 ID 및 환경을 유지하십시오. 상태 쿼리, 복구, 조정 및 webhook 처리 중에 해당 환경을 유지하세요. 시간 초과 후에는 원래 환경을 생략하거나 새 주문 번호를 사용하여 다시 시도하지 마십시오.

자금/계약 이전은 하나의 환경 내에서 유지됩니다. 모의자금은 생산자금이 될 수 없습니다. 별도의 파트너측 시뮬레이션 회계 및 `SIM-`와 같은 인식 가능한 주문 접두어를 사용하세요.

<span id="simulated-integration-sequence" data-sixmm-canonical-anchor="simulated-integration-sequence" aria-hidden="true"></span>

## 시뮬레이션된 통합 시퀀스

1. 사용자를 바인딩하고 공개 플랫폼 사용자 ID를 저장합니다.
2. 명시적인 `SIMULATED`로 잔액을 쿼리하고 필요한 경우 자금을 포함합니다.
3. 소규모의 시뮬레이션 자금 이체를 생성하고 원래 비즈니스 주문을 유지합니다.
4. 전용 자금 상태 쿼리를 통해 최종 결과를 확인하세요.
5. `demo` 모드에서 대상 초 페이지를 열거나 포함합니다.
6. 동일한 시뮬레이션 지갑을 조회하여 실제 이체 금액을 조정합니다.
7. 무기한 거래를 테스트하려면 시뮬레이션 자금을 시뮬레이션 계약으로 이전하고 시뮬레이션 선물 프런트엔드를 사용하세요. 6개의 파트너 영구 쿼리는 시뮬레이션된 거래 내역을 검증할 수 없습니다.

<span id="acceptance-checklist" data-sixmm-canonical-anchor="acceptance-checklist" aria-hidden="true"></span>

## 수락 체크리스트

| 대본 | 검증할 증거 |
| --- | --- |
| 신원 | 바인딩된 사용자 매핑이 저장됩니다. 다른 파트너의 사용자는 쿼리할 수 없습니다. |
| 입증 | 리디렉션 및 삽입 흐름은 새로운 자격 증명을 사용합니다. 서명은 자금 주문을 생성하지 않습니다. |
| 자금 | 양측은 실제 금액과 최종 상태에 동의합니다. |
| 알 수 없는 결과 | 복구는 두 번째 전송을 생성하지 않고 원래 순서를 사용합니다. |
| 환경 격리 | 시뮬레이션된 백엔드와 프런트엔드 대상이 일치합니다. 생산 잔액은 영향을 받지 않습니다. |
| 쿼리 | 필수 사용자/범주 필터, 밀리초 창, 빈 페이지 및 커서가 처리됩니다. |
| 비율 제한 | 모든 쿼리 호출자는 제한을 공유하고 원래 실패한 페이지를 다시 시도합니다. |
| 저장 | 금액과 ID는 문자열로 유지됩니다. 엔터티 레코드는 멱등적으로 저장됩니다. |

프로덕션으로 전환하기 전에 백엔드 자금 목표와 프런트엔드 모드를 모두 변경하세요. 보류 중인 주문은 원래 환경에서 계속 복구됩니다.
