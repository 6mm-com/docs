<h2 id="recommended-combination">Combinação recomendada</h2>

| Objetivo do parceiro | Frontend | Backend | Porque é que isso importa |
| --- | --- | --- | --- |
| Adicionar um terminal de negociação embutido | Trading Widget SDK | Agent SDK | O widget gere a interface de negociação enquanto o backend parceiro emite tokens e mantém os segredos privados. |
| Criar um ponto de entrada nativo para a aplicação | Entrada nativa ou H5 | Agent SDK | A aplicação abre uma 6MM de entrada URL depois de o parceiro validar a sessão do utilizador. |
| Construa um fluxo de negociação personalizado | UI Parceiro | Revelador API + fluxos SDK selecionados | Use APIs para dados de conta, ordens, posição e mercado, mantendo os controlos operacionais do lado do servidor. |

<h2 id="reference-architecture">Arquitetura de referência</h2>

```text
Partner Web App
  -> TradingWidget.create()
  -> tokenProvider()
  -> Partner Backend
  -> 6MM Agent SDK
  -> 6MM Agent API
  -> 6MM Trading iframe
```

> **Guarda segredos do lado do servidor**
>
> O código do navegador só deve chamar endpoints pertencentes ao parceiro. O Agente API segredo nunca deve ser enviado para o código frontend.

<h2 id="production-checklist">Lista de verificação de produção</h2>

- Armazenar apiSecret apenas na infraestrutura backend.
- Usar HTTPS para pedidos de API do Agente e URLs de webhooks.
- Persistir agentUserId, platformUserId, e agentOrderNo mapeamentos.
- Representar valores monetários como cadeias decimais em vez de valores de ponto flutuante.
- Tratar PROCESSING como pendente, não como sucesso ou fracasso.
- Processar webhooks idempotentemente porque se esperam retentativas.
