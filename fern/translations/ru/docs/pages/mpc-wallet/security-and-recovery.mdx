Подготовка к обеспечению безопасности начинается с выбора режима хранения. Защита учетной записи, одобрение транздоли криптографического ключа, участие MPC и материалы для восстановления служат разным целям.

<span id="assign-responsibilities" data-sixmm-canonical-anchor="assign-responsibilities" aria-hidden="true"></span>

## Распределите обязанности

Отдельный рутинный просмотр, инициирование передачи, утверждение, администрирование участников и управление учетными данными разработчиков, если это позволяет продукт. Проверьте разрешения в предполагаемой рабочей области; доступ к одному рабочему пространству не дает полномочий над другим.

Для корпоративных рабочих процессов договоритесь, кто будет проверять изменения пунктов назначения и исходящие запросы. Для подписания устройства участник должен проверить отображаемую сеть, актив, сумму, место назначения и контекст, прежде чем принять решение. Подтверждение устройства не следует рассматривать как слепой запрос на одобрение.

<span id="keep-credentials-distinct" data-sixmm-canonical-anchor="keep-credentials-distinct" aria-hidden="true"></span>

## Сохраняйте учетные данные отдельными

| Материал | Цель |
| --- | --- |
| Аутентификация учетной записи | Доступ к пользовательскому приложению |
| API ключ и секрет | Аутентификация серверных запросов API |
| Ключ авторизации клиента | Авторизуйте содержимое вывода API там, где это необходимо. |
| MPC общий ключ | Участвовать в процессе распределенной подписи кошелька |
| Материалы для резервного копирования и восстановления | Восстановите участие или выполните поддерживаемую процедуру восстановления. |

Храните их в соответствии со своими обязанностями. Ключ API не является общим ресурсом MPC; сброс пароля учетной записи не является операцией по восстановлению кошелька. Загружайте открытые ключи только через соответствующий процесс регистрации, а не соответствующие им закрытые ключи.

## Подготовьте восстановление перед использованием

Запишите необходимых участников, владельцев резервных копий и шаги восстановления во время регистрации. Храните резервные копии в отдельных местах и ​​тестируйте поддерживаемую процедуру восстановления в контролируемой среде. Рассмотрим как потерянное устройство, так и сбой в работе платформы.

Самостоятельное хранение не позволяет платформе воссоздавать недостающие доли клиентов. Если останется слишком мало пригодных для использования участников и резервных копий для удовлетворения требований кошелька, доступ к активам может быть потерян. Совместное хранение ключей также требует документированного соглашения о взыскании; не думайте, что участие в платформе гарантирует выздоровление.

<span id="handle-an-unavailable-participant" data-sixmm-canonical-anchor="handle-an-unavailable-participant" aria-hidden="true"></span>

## Обработка недоступного участника

Сначала определите временную проблему с подключением, недоступное устройство и потерю материала для подписи. Просмотрите состояние сеанса и устройства, а затем воспользуйтесь поддерживаемым процессом восстановления или замены. Не удаляйте устройство, не меняйте его удостоверение подписи приложения и не предполагайте, что общие ресурсы могут быть перемещены, прежде чем проверять требования к восстановлению.

Доступность резервной копии не является доказательством завершения теста восстановления. Прежде чем полагаться на них, убедитесь, какие процедуры и инструменты включены в ваш релиз.
