Это руководство предназначено для **Agent Java SDK `v0.3.0`** и Java 8+.

<span id="choose-both-the-frontend-mode-and-the-funds-environment" data-sixmm-canonical-anchor="choose-both-the-frontend-mode-and-the-funds-environment" aria-hidden="true"></span>

## Выберите как внешний режим, так и среду фондов.

Настройте среду средств серверной части партнера отдельно от режима внешней торговли. Привязка и учетные данные для входа являются общими; выпуск билета или токена не выбирает кошелек и не перемещает средства.

| Конфигурация | Производство | Имитация |
| --- | --- | --- |
| Привязка и аутентификация | Общая привязка пользователя и одноразовые учетные данные | Та же личность и аутентификация |
| Новые переводы и балансы пользователей | Опустите `environment` или используйте `PRODUCTION` | Явно используйте `SIMULATED` |
| Финансирование восстановления первоначального заказа | Используйте сохраненную исходную среду | Используйте сохраненную исходную среду |
| Виджет режима торговли | `tradingMode=real` | `tradingMode=demo` |
| Цель внешнего интерфейса HTTP/WS | Производственный объект предоставлен 6MM | Имитированная цель предоставлена ​​6MM |
| Шесть запросов к постоянным данным | Производственные данные | Нет выбора среды; эти методы не запрашивают смоделированные данные |

Для `wallet-transfer-status` при отсутствии `environment` используется сохраненная среда исходного заказа, включая смоделированный заказ. Явно конфликтная среда отвергается. Предпочитайте сохранять среду и передавать ее явно при восстановлении операции.

`isSimulatedUser` описывает учетную запись. Он не направляет новые запросы в имитируемый кошелек. Если пропустить `environment` в новом запросе средств, производство по-прежнему будет выбрано, даже если флаг учетной записи имеет значение true.

<span id="supported-java-request-models" data-sixmm-canonical-anchor="supported-java-request-models" aria-hidden="true"></span>

## Поддерживаемые модели запроса Java

Эти запросы поддерживают `withEnvironment(ExecutionEnvironment.SIMULATED)`:

- `TransferRequest`, `TransferAllOutRequest`, `ReverseOrderRequest`.
- `QueryOrderRequest`, `ListOrdersRequest`.
- `QueryUserAssetsRequest`.
- `WalletTransferRequest`, `WalletTransferQueryRequest`.

`bind`, `queryAccount`, `createEntryUrl`, `createEmbedToken` и шесть моделей запросов с постоянным запросом не выбирают среду финансирования.

```java
import com.sixmm.agent.model.ExecutionEnvironment;
import com.sixmm.agent.model.QueryUserAssetsRequest;
import com.sixmm.agent.model.QueryUserAssetsResponse;

QueryUserAssetsResponse assets = client.queryUserAssets(
        QueryUserAssetsRequest.of("1188041528")
                .withFunding()
                .withEnvironment(ExecutionEnvironment.SIMULATED));
```

Инициализируйте `client` с помощью [Быстрый старт](/ru/sdk/agent-sdk/java/quick-start) и используйте общедоступный идентификатор пользователя из сохраненной привязки.

<span id="preserve-the-original-environment" data-sixmm-canonical-anchor="preserve-the-original-environment" aria-hidden="true"></span>

## Сохраните исходную среду

Сохраните тип интерфейса, `agentOrderNo`, идентификатор пользователя и среду перед отправкой запроса на средства. Сохраняйте эту среду во время запросов статуса, восстановления, согласования и обработки webhook. По истечении времени ожидания никогда не повторяйте попытку, опуская исходную среду или используя новый номер заказа.

Передача средств/контрактов остается в одной среде. Имитированные фонды не могут стать производственными фондами. Используйте отдельный моделируемый учет на стороне партнера и узнаваемые префиксы заказов, такие как `SIM-`.

<span id="simulated-integration-sequence" data-sixmm-canonical-anchor="simulated-integration-sequence" aria-hidden="true"></span>

## Моделируемая последовательность интегрирования

1. Привяжите пользователя и сохраните идентификатор пользователя общедоступной платформы.
2. Запрашивайте балансы с явным указанием `SIMULATED` и при необходимости включайте финансирование.
3. Создайте небольшой смоделированный перевод финансирования и сохраните исходный бизнес-заказ.
4. Подтвердите окончательный результат с помощью специального запроса о статусе финансирования.
5. Откройте или встройте целевую страницу секунд в режиме `demo`.
6. Запросите те же смоделированные кошельки и сверьте фактическую переведенную сумму.
7. Чтобы протестировать бессрочную торговлю, перенесите моделируемое финансирование в моделируемый контракт и используйте интерфейс моделируемого фьючерса. Шесть постоянных запросов партнеров не могут проверить смоделированную торговую историю.

<span id="acceptance-checklist" data-sixmm-canonical-anchor="acceptance-checklist" aria-hidden="true"></span>

## Контрольный список приемки

| Сценарий | Доказательства для проверки |
| --- | --- |
| Личность | Привязанное сопоставление пользователей сохраняется; Запрос пользователей другого партнера невозможен. |
| Аутентификация | Потоки перенаправления и внедрения используют новые учетные данные; подписание не создает денежных поручений. |
| Фонды | Обе стороны согласовывают фактическую сумму и окончательный статус. |
| Неизвестный результат | При восстановлении используется исходный заказ без создания второго перевода. |
| Изоляция окружающей среды | Моделируемые цели внутренней и внешней части совпадают; баланс производства не изменяется. |
| Запросы | Обрабатываются необходимые фильтры пользователей/категорий, миллисекундные окна, пустые страницы и курсоры. |
| Ограничения ставок | Все вызывающие запросы совместно используют регулирование и повторяют попытку исходной неудачной страницы. |
| Хранилище | Суммы и идентификаторы остаются строками; записи сущностей сохраняются идемпотентно. |

Прежде чем переключиться на производство, измените целевое значение внутренних средств и режим внешнего интерфейса. Отложенные ордера продолжают восстанавливаться в исходной среде.
