Webhooks notifica a un socio backend sobre cambios asincrónicos en el estado del negocio. Debido a que se puede volver a intentar la entrega, cada receptor debe verificar la firma antes de analizar los datos confiables y debe procesar el evento de manera idempotente.

<span id="webhook-headers" data-sixmm-canonical-anchor="webhook-headers" aria-hidden="true"></span>

## Webhook encabezados

| Encabezamiento | Descripción |
| --- | --- |
| Marca de tiempo del Agente X | Marca de tiempo de Unix en segundos. |
| Agente X-Nonce | Nonce de protección de reproducción. |
| Firma del agente X | HMAC-SHA256 firma. |

```text
timestamp + nonce + rawBody
```

Utilice el cuerpo exacto de la solicitud sin procesar recibido durante HTTP al reconstruir el valor firmado. Analizar y volver a serializar JSON primero puede cambiar los espacios en blanco o el orden de los campos y producir una firma diferente.

<span id="verification-flow" data-sixmm-canonical-anchor="verification-flow" aria-hidden="true"></span>

## Flujo de verificación

1. Lea los encabezados de marca de tiempo, nonce y firma.
2. Capture el cuerpo de la solicitud sin modificar.
3. Construya `timestamp + nonce + rawBody`.
4. Calcula HMAC-SHA256 con el socio API secreto.
5. Compare las firmas calculadas y recibidas mediante una comparación de tiempo constante.
6. Aplique las comprobaciones aprobadas de frescura y no reutilización de la marca de tiempo.
7. Analice y procese el evento solo después de que la verificación sea exitosa.

Cuando esté disponible un verificador oficial Agent SDK, utilícelo en lugar de mantener un código de firma independiente.

<span id="order-idempotency" data-sixmm-canonical-anchor="order-idempotency" aria-hidden="true"></span>

## Idempotencia del orden

| Caso | Manejo |
| --- | --- |
| Solicitud de transferencia inicial | Cree un agentOrderNo único a nivel mundial. |
| HTTP tiempo de espera | Consulta el agentOrderNo original antes de crear uno nuevo. |
| PROCESSING respuesta | Espere a webhook o consulte el estado del pedido. |
| webhook repetido | Deduplicar por clave de idempotencia y estado final. |

<span id="recommended-idempotency-record" data-sixmm-canonical-anchor="recommended-idempotency-record" aria-hidden="true"></span>

## Registro de idempotencia recomendado

Almacene suficiente información para reconocer una entrega repetida y recuperarla de forma segura:

| Campo | Objetivo |
| --- | --- |
| Clave de evento o negocio | Identifica de forma única la notificación u operación. |
| Número de pedido del socio | Conecta el evento a la solicitud original. |
| hash de carga útil | Ayuda a identificar cargas útiles repetidas y conflictivas. |
| Estado de procesamiento actual | Distingue el trabajo recibido, procesado, exitoso y fallido. |
| Estado comercial final | Evita que una acción terminal se aplique dos veces. |
| Marca de tiempo procesada | Apoya las políticas de investigación y retención. |

Confirme el cambio de negocio y el registro de idempotencia en la misma transacción cuando sea posible. Un evento repetido debería devolver el resultado ya conocido en lugar de aplicar nuevamente el saldo, el pedido o el cambio de usuario.

<span id="timeout-and-retry-rule" data-sixmm-canonical-anchor="timeout-and-retry-rule" aria-hidden="true"></span>

## Regla de tiempo de espera y reintento

Un tiempo de espera de HTTP no prueba que la solicitud original haya fallado. Consulte la operación utilizando el `agentOrderNo` original, o espere su webhook, antes de decidir si se requiere otra acción. Crear un nuevo número de orden comercial después de cada tiempo de espera puede provocar movimientos de fondos duplicados.

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## Lista de verificación de producción

- Verifique la firma antes de JSON análisis o procesamiento comercial.
- Conserve el cuerpo sin procesar independientemente de la carga útil analizada.
- Rechace solicitudes obsoletas o reproducidas de acuerdo con la política de integración aprobada.
- Haga que el procesamiento de eventos sea seguro para entregas repetidas y fuera de orden.
- Registre los ID de eventos, los números de pedidos de los socios, el resultado del procesamiento y la hora de la solicitud.
- Redactar secretos y valores de firma de registros y archivos adjuntos de soporte.

## Límites de financiación y medio ambiente

El flujo de transferencia de contrato original webhook y `queryOrder` no se aplica automáticamente a la financiación. Confirme las operaciones de financiación utilizando `queryWalletTransfer` y el entorno de pedido original. Usos de la financiación `status`; Las respuestas originales de transferencia de contrato utilizan `orderStatus`. Una respuesta HTTP exitosa o `code=0` no prueba por sí sola que se hayan movido fondos.

Las notificaciones explícitas de transferencia de contrato simuladas incluyen `environment=SIMULATED`. Primero verifique el cuerpo sin procesar, luego verifique el usuario, el monto, la identidad del pedido y el entorno con el pedido comercial local guardado.
