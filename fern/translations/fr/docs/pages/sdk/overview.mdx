## Combinaison recommandée

| Objectif partenaire | Frontend | Backend | Pourquoi cela compte |
| --- | --- | --- | --- |
| Ajouter un terminal de trading intégré | Trading Widget SDK | Agent SDK | Le widget gère l’interface de trading tandis que le partenaire en arrière-plan émet les jetons et garde les secrets privés. |
| Créez un point d’entrée natif pour une application | Entrée native ou H5 | Agent SDK | L’application ouvre une 6MM URL d’entrée après que le partenaire ait validé la session utilisateur. |
| Construisez un flux de trading personnalisé | UI partenaire | Révélateur API + flux de SDK sélectionnés | Utilisez API pour les données de compte, d’ordre, de position et de marché tout en conservant les contrôles opérationnels côté serveur. |

<span id="reference-architecture" data-sixmm-canonical-anchor="reference-architecture" aria-hidden="true"></span>

## Architecture de référence

```text
Partner Web App
  -> TradingWidget.create()
  -> tokenProvider()
  -> Partner Backend
  -> 6MM Agent SDK
  -> 6MM Agent API
  -> 6MM Trading iframe
```

> **Gardez des secrets côté serveur**
>
> Le code du navigateur ne doit appeler que les terminaux appartenant au partenaire. Le secret de l’Agent API ne doit jamais être envoyé au code frontend.

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## Liste de contrôle de la production

- Stocker apiSecret uniquement dans l’infrastructure backend.
- Utiliser HTTPS pour les requêtes d' API d’agent et les URL de webhook.
- Persister agentUserId, platformUserId, et agentOrderNo mappings.
- Représenter les montants monétaires sous forme de chaînes décimales au lieu de valeurs en virgule flottante.
- Traiter PROCESSING comme étant en attente, et non comme un succès ou un échec.
- Traiter les webhooks de manière idempotente car des réessayages sont attendus.
