使用對話歷史記錄恢復上下文、檢查服務品質並調查特定諮詢。從對話號碼或狹窄的時間範圍開始，而不是瀏覽每筆記錄。

<div className="sixmm-support-flow">

1. **尋找會話** — 選擇篩選器和正確的日期基礎。
2. **閱讀完整的上下文** — 查看訊息、代理商和訪客詳細資訊。
3. **跟進** — 改進答案或繼續未解決的案例。

</div>


<span id="find-an-earlier-conversation" data-sixmm-canonical-anchor="find-an-earlier-conversation" aria-hidden="true"></span>

## 尋找較早的對話

開啟**對話歷史記錄**。使用可用的使用者/會話搜尋、對話類型、評級、代理、類別、語言和時間過濾器。開啟詳細資訊以閱讀訊息和會話資訊。

使用者電子郵件清單列首選聯絡電子郵件，否則使用訪客電子郵件。詳細資訊視圖保留這兩個字段，以便代理可以區分其來源。空值表示該欄位未被收集；它並不能證明客戶沒有電子郵件帳戶。

<span id="review-service-quality" data-sixmm-canonical-anchor="review-service-quality" aria-hidden="true"></span>

## 審查服務品質

結合對話、代理和評級來了解案件。顯示為 AI 訊息的回應可能來自配置的答案或匹配階段，而不是大型模型呼叫。將內容與當前知識進行比較，並在調查回應行為時使用流程測試。

只有具有相關權限才能進行刪除。刪除一筆或多筆記錄前請先閱讀確認資訊。 MCP歷史查詢使用授權範圍，刪除需要確認；不要假設每個代理都可以獲得完整的租戶歷史記錄。


<span id="read-the-fields-without-mixing-identities" data-sixmm-canonical-anchor="read-the-fields-without-mixing-identities" aria-hidden="true"></span>

## 讀取欄位而不混合身份

| 場地 | 解釋 |
| --- | --- |
| 通話號碼 | 標識您正在查看的諮詢。使用它可以避免混淆單獨的會話。 |
| 訪客姓名 | 可讀的顯示標籤，而不是經過驗證的交易帳戶的證明。 |
| 條目類型和使用者 ID | 幫助區分匿名存取和整合登入身分。不應猜測遺失的身份資料。 |
| 使用者信箱 | 首先使用聯絡電子郵件，然後使用訪客電子郵件；細節將兩個來源分開。 |
| 語言和 IP 位置 | 用於支援的有用上下文，而不是用戶身份或確切物理位置的證明。 |
| 等級 | 該會話存在的回饋。沒有評級與負面評級不同。 |

<span id="example-review-a-low-rated-consultation" data-sixmm-canonical-anchor="example-review-a-low-rated-consultation" aria-hidden="true"></span>

### 範例：查看評分較低的諮詢

1. 根據需要按日期、代理和評級進行篩選，然後開啟完整記錄。
2. 在評估答案之前先閱讀訪客提出的問題。檢查交接或語言誤解是否影響了對話。
3. 如果答案不完整，請查看相應的知識內容和機器人配置。糟糕的結果並不總是意味著模型本身失敗。
4. 將會話編號保留在內部跟進中，以便團隊可以返回相同的證據。

## 常見問題

<AccordionGroup>

<Accordion title="為什麼電子郵件是空白的？">
會話可能尚未收集聯絡電子郵件或收到來自條目整合的電子郵件。在得出資料意外遺失的結論之前，請詳細檢查這兩個欄位。
</Accordion>

<Accordion title="為什麼更改日期過濾器會改變結果？">
該頁面可以按開始時間或關閉時間進行過濾。某天開始、另一天結束的對話在這兩種選擇下屬於不同的結果。
</Accordion>

</AccordionGroup>
