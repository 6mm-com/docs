Webhooks 通知合作伙伴後端有關異步業務狀態更改的信息。由於可能會重試傳遞，因此每個接收者都必須在解析可信數據之前驗證簽名，並且必須冪等地處理事件。

<span id="webhook-headers" data-sixmm-canonical-anchor="webhook-headers" aria-hidden="true"></span>

## Webhook 標頭

| 標頭 | 描述 |
| --- | --- |
| X-代理時間戳 | Unix 時間戳（以秒為單位）。 |
| X-代理-隨機數 | 重放保護隨機數。 |
| X-代理簽名 | HMAC-SHA256簽名。 |

```text
timestamp + nonce + rawBody
```

重建簽名值時，使用通過 HTTP 收到的確切原始請求正文。首先解析和重新序列化 JSON 可以更改空格或字段順序併產生不同的簽名。

<span id="verification-flow" data-sixmm-canonical-anchor="verification-flow" aria-hidden="true"></span>

## 驗證流程

1. 讀取時間戳、隨機數和簽名標頭。
2. 捕獲未修改的原始請求正文。
3. 構建`timestamp + nonce + rawBody`。
4. 使用夥伴 API 秘密計算 HMAC-SHA256。
5. 使用恆定時間比較來比較計算出的簽名和接收到的簽名。
6. 應用批准的時間戳新鮮度和隨機數重用檢查。
7. 驗證成功後才解析並處理該事件。

當官方 Agent SDK 驗證器可用時，使用它而不是維護獨立的簽名代碼。

<span id="order-idempotency" data-sixmm-canonical-anchor="order-idempotency" aria-hidden="true"></span>

## 順序冪等性

| 案件 | 處理 |
| --- | --- |
| 初始轉移請求 | 創建一個全球唯一的 agentOrderNo。 |
| HTTP 超時 | 在創建新的之前查詢原始的 agentOrderNo。 |
| PROCESSING 回覆 | 等待webhook或查詢訂單狀態。 |
| 重複webhook | 按冪等鍵和最終狀態進行重複數據刪除。 |

<span id="recommended-idempotency-record" data-sixmm-canonical-anchor="recommended-idempotency-record" aria-hidden="true"></span>

## 推薦冪等記錄

存儲足夠的信息以識別重複交付並安全恢復：

| 場地 | 目的 |
| --- | --- |
| 活動或業務密鑰 | 唯一標識通知或操作。 |
| 合作伙伴訂單號 | 將事件連接到原始請求。 |
| 有效負載哈希 | 幫助識別衝突的重複負載。 |
| 當前處理狀態 | 區分接收、處理、成功和失敗的工作。 |
| 最終經營狀況 | 防止終端操作被應用兩次。 |
| 處理時間戳 | 支持調查和保留策略。 |

儘可能在同一事務中提交業務變更和冪等記錄。重複的事件應該返回已知的結果，而不是再次應用餘額、訂單或用戶更改。

<span id="timeout-and-retry-rule" data-sixmm-canonical-anchor="timeout-and-retry-rule" aria-hidden="true"></span>

## 超時和重試規則

HTTP 超時並不能證明原始請求失敗。使用原始的 `agentOrderNo` 查詢操作，或等待其 webhook，然後再決定是否需要執行其他操作。每次超時後創建新的業務訂單號可能會導致重複的資金流動。

<span id="production-checklist" data-sixmm-canonical-anchor="production-checklist" aria-hidden="true"></span>

## 生產清單

- 在JSON解析或業務處理之前驗證簽名。
- 獨立於解析的有效負載保留原始主體。
- 根據批准的集成策略拒絕過時或重播的請求。
- 確保事件處理對於重複和無序交付來說是安全的。
- 記錄事件 ID、合作伙伴訂單號、處理結果和請求時間。
- 編輯日誌和支持附件中的機密和簽名值。

## 資金和環境邊界

原始合同轉賬 webhook 和 `queryOrder` 流程不會自動應用於資金。使用`queryWalletTransfer`和原始訂單環境確認資金操作。資金用途`status`；原始合同傳輸響應使用`orderStatus`。成功的 HTTP 響應或 `code=0` 本身並不能證明資金已轉移。

顯式模擬合約轉移通知包括`environment=SIMULATED`。首先驗證原始主體，然後根據保存的本地業務訂單檢查用戶、金額、訂單身份和環境。
